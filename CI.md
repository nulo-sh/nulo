# CI guide

Contributor-facing reference for what runs when, how to opt in to slow gates, how to release, and how to debug a failing PR. The implementation details (workflow YAMLs, composite actions, reusables) live in [`.github/`](./.github/); the design rationale lives in [`implementations-plan/archive/ci-cd/`](./implementations-plan/archive/ci-cd/).

## Branch model

- **`main`** — stable. Hot off this branch is the version we'd ship to users.
- **`dev`** — integration trunk. Day-to-day PRs land here.
- **Feature branches** (`feat/...`, `fix/...`, `docs/...`, `chore/...`) — short-lived, PR'd into `dev`. Auto-deleted on merge.
- **No long-lived feature branches.** A `dev → main` PR is the "promote to stable" step.

## What runs when

| Trigger | Workflow(s) | Wall time |
|---|---|---|
| Push to a feature branch (no PR) | local pre-commit hook only (biome + commitlint) | <1 s |
| Open / sync PR to `dev` | `pr-quick` always; `pr-extension-smoke-e2e` + `pr-extension-network-e2e` when their filters trip or their label is set | 3–10 min (`pr-quick`); +5–10 min each if smoke / network triggers |
| Open / sync PR to `main` | `pr-quick` always; each e2e lane when its filter trips on the PR's diff (a promote's is everything since the last one) or its label is set | 10–12 min (`pr-quick`); 15–25 min when the lanes run |
| Add the `e2e:extension-smoke` or `e2e:extension-network` label | the corresponding workflow runs (removing the label re-evaluates) | as above |
| Push to `main` | `release.yml` (release-please opens or updates a Release PR; merging it tags + creates the GitHub Release + attaches built artifacts) | 1–2 min for the PR refresh; 15–25 min for the publish run after merge |
| Click "Run workflow" on `release.yml` | re-publish artifacts for an existing tag (escape hatch) | 15–25 min |
| Click "Run workflow" on `pr-extension-network-e2e.yml` or `pr-extension-network-e2e-firefox.yml` | that browser's whole network lane at retry 0 on the chosen ref; a second dispatch on the same commit cancels the first | ~10–20 min |
| Click "Run workflow" on `extension-network-e2e-soak.yml` | the named network files, `repeats` times in sequence at retry 0 on Chrome, every named test required to pass ([§ the soak](#extension-network-e2e-soakyml)) | one job per iteration, up to 30 min each |
| Merge a change to `infra/token-list/list.source.json` into `dev`, or click "Run workflow" on `publish-token-list.yml` from `dev` | tree check and review summary; after the `token-list` environment approval, sign and open the publish PR | 1–2 min plus the approval wait |
| Click "Run workflow" on `publish-packages.yml` | test, stage, pack and digest-check the three npm packages; publish and verify them only with `dry_run` false and the `npm-publish` environment approved | 1–2 min as a dry run; a publish adds the approval wait, then 2–17 min (`verify` polls the registry for up to 15 min) |

### `pr-quick.yml`

Always runs on every PR. Lightweight gates:

- `commitlint` — Conventional Commits (`feat:`, `fix:`, `chore:`, `docs:`, …; lower-case subject, 100-char header cap). On PRs to `dev`: every commit in `base..head`, except on the `main → dev` sync PR (head branch `sync/main-to-dev*`), whose range is `main`'s already-merged history, and on Dependabot's PRs (PR author `dependabot[bot]`, never the branch name or the last pusher): Dependabot guesses the case of `bump` from `dev`'s recent history, so its commits can read `Bump`, and the squash drops them; the merger lower-cases the title that lands ([CLAUDE.md § Dependency policy](./CLAUDE.md#dependency-policy)). No job lints a PR's title. On PRs to `main`: **skipped** — the promote PR's merge subject is an intentional release-note line (`release: promote dev → main …`) that runs past the 100-char cap, the bot Release PR (`chore(main): release X.Y.Z`) is reliably conventional anyway, and the dev squash subjects in the range are already-merged + immutable (re-linting them can only fail the required check on a long subject, never fix it).
- `lint-and-typecheck` — biome over the repo (root `scripts/` included) + `bun run typecheck:all` (each workspace's `typecheck`: vue-tsc for the extension and `design`, tsc for the rest; the extension's also covers its `scripts/`, its Vite configs and its e2e tree, and `typecheck:scripts` covers the root `scripts/` tree), and `bun audit` at every severity through `scripts/ci-cd/audit-gate.ts`. The audit fails the job only when `Detect changes` set `audit-mode` to `enforce` (a PR whose `bun.lock`, `package.json`, `bunfig.toml` or `scripts/ci-cd/audit-acks.json` diff is more than `"version"` lines) and an advisory has no matching entry in `audit-acks.json`, an entry matches no advisory, or the audit's output cannot be read; every other run writes the same summary without failing (SECURITY.md, Dependency policy).
- `unit-tests` — `bun run test:all` (every workspace's `test` script; `--if-present` skips only `playground`, which has no `test` script — `landing` has one and runs). Every workspace `test` script but three is `bun --bun vitest run`, so those suites execute on the pinned Bun (`setup-bun`), not on the runner image's ambient Node; `infra/passkey-rp` and `infra/subscribe` run `bun test`, while `resolve-asset`'s plain `vitest run` and the Puppeteer e2e jobs still run vitest under Node.
- `build-extension` — chrome + firefox builds, both on every PR that builds the extension, uploaded as the `extension-chrome` / `extension-firefox` artifacts (7-day retention) with the version stamped `X.Y.Z-pr.<N>` (`version_suffix`). The advisory `preview-comment` job keeps ONE sticky comment on the PR linking to them, edited in place on every push (a run whose head the PR has since moved past leaves the comment alone, so a slow run never overwrites a newer one) — download, unzip, **Load unpacked**. Same-repo PRs only; `continue-on-error` and not in `quality-status`'s `needs`, so it can red neither the run nor the gate. Logic in `scripts/ci-cd/preview-comment.ts`.
- `build-landing` — `bun run build` of `apps/landing`, the production build (the generated legal pages, then `vite build`; no network), then a check that the pages shipped (How Aztec works, `/subscribed` and the legal pages); runs when the landing, `legal/`, its dependency libraries, a workflow or the root config changes.
- `build-storybook` — `bun run --cwd apps/extension build-storybook`, on the extension build's condition (every story lives under its filter), with `STORYBOOK_DISABLE_TELEMETRY=1` so CI sends nothing to Storybook. It builds the stories; it runs no visual test.
- `launch-legal` — on every PR into `main` only: `packages/legal/src/launch.test.ts` with `NULO_LAUNCH_GATE=1`, which fails when the root `package.json` version is a stable release at or above 1.0.0 and `legal/terms.md` or `legal/privacy.md` still holds a `«FILL`. A 0.x release, a prerelease and every PR into `dev` pass by construction, so legal drafts can land on `dev`. A second step runs `apps/landing/scripts/legal-pages.test.ts` with the same switch, which fails when `legal/website-privacy.md` holds a `«FILL` at any version: nulo.sh publishes it from `main`, and the wallet's check does not read it. A PR retargeted to `main` gets no new run and an `--admin` merge skips the check, so `auto-unstick` runs the same check before it creates a stable tag (the [`release` skill](./.claude/skills/release/SKILL.md)).

The `quality-status` aggregator at the end is the required check on `main` / `dev` branch protection (the bare job/check-run name; a `Workflow / Job` context such as `Quality / Status` never matches a produced check — see [CLAUDE.md § Branching](./CLAUDE.md#branching--merging) and `implementations-plan/archive/required-check-mismatch/`). Like the e2e aggregators it is an exact state machine, not a list of bad results: `Detect changes` must succeed, its build flags must read `true` or `false`, and every gate must end as its own `if:` asks (`success` when it runs, `skipped` only where its condition did not hold: a build whose filter did not trip, the Storybook build included, commitlint on a manual dispatch, or `launch-legal` outside a PR into `main`), so a gate that never ran fails the check.

### `pr-extension-smoke-e2e.yml`

Runs the smoke e2e suite (`vitest.e2e.config.ts`) as a **3-shard matrix**, each runner about a third of the files' recorded time ([shard timings](./apps/extension/tests/e2e/README.md#ci-sharding-5-way-matrix)), because a whole Firefox run neared the 30-minute job limit; the Firefox twin runs the same shards. No Aztec sandbox; just puppeteer driving the popup UI.

Triggers:
- **Auto** on PRs to `dev` or `main` whose diff touches the `smoke-surface` paths-filter (popup, components, manifest, the wallet services smoke exercises, build inputs, the harness, etc. — see [`pr-extension-smoke-e2e.yml`](./.github/workflows/pr-extension-smoke-e2e.yml) `filters:`)
- **Manual** by adding the `e2e:extension-smoke` label

The seeded profile chaos files (`profile-chaos.test.ts`, smoke and network) skip unless `NULO_E2E_CHAOS=1` arms them, which no smoke job sets and the network lane sets only for its `send-chaos` job; they are local runs ([README § Chaos runs](./apps/extension/tests/e2e/README.md#chaos-runs)).

`extension-smoke-e2e-status` emits `pass` when the suite is skipped (no relevant changes / no label), so branch protection sees a green check either way. When the suite runs, GitHub hands the aggregator the three shards as one result, so a failed or cancelled shard reds it, and a re-run of one shard does not change that while another shard's failure stands: on a scratch probe, re-running one failed leg of a three-leg matrix (plain jobs, and legs calling a reusable workflow as the lanes do) re-ran the dependent aggregator at the same attempt, which still read the matrix as `failure` ([run 38013958157](https://github.com/nulo-sh/nulo/actions/runs/38013958157), 2026-10-10; [#168](https://github.com/nulo-sh/nulo/issues/168)). Re-run one shard or every failed job as you like; re-deciding a skip takes "Re-run all jobs" (see "Concurrency"). It is a **required** check on both `dev` and `main` (see "Check names and the protection runbook").

### `pr-extension-network-e2e.yml`

Runs the network e2e suite (anvil + Aztec sandbox + playground + the extension build) as a **5-shard parallel matrix** — each shard owns its own sandbox + about a fifth of the pool's recorded time (the pool is the suite less the twelve files the heavy, canary and chaos jobs run). The split comes from `apps/extension/tests/e2e/shard-timings.json`, which `bun scripts/ci-cd/e2e-timings.ts` rewrites from these lanes' job logs; a file it lacks lands on the lightest shard. Two long files run in a heavy job of their own (`Run / heavy / snack-placement + failed-send-check`) for wall time alone: folded into the five shards, they made the lane end later on both browsers in one measured pair per browser ([#972](https://github.com/nulo-sh/nulo/issues/972)). Wall time ~10–20 min (vs ~35–45 min unsharded). The pool, the dedicated jobs and the chaos seeds live once, in [`_extension-network-e2e-lane.yml`](./.github/workflows/_extension-network-e2e-lane.yml), which this workflow, its Firefox twin, the nightly and `release.yml`'s opt-in run each call as one job (`Run`, the nightly's Firefox leg `Firefox / Run`), so every check-run reads `Run / <lane job> / network suite…`; a caller hands it only the commit, browser, retry, kill switch and (the nightly alone) a chaos seed, and `scripts/ci-cd/behavior-gating.test.ts` pins every caller's row and the lane's shape. Same trigger shape as `pr-extension-smoke-e2e`, but with the `extension-network` filter (network-touching wallet code, runtime, `wallet-bridge`, playground, etc.) and the `e2e:extension-network` label. See [`apps/extension/tests/e2e/README.md`](./apps/extension/tests/e2e/README.md#ci-sharding-5-way-matrix) for the shard-design rationale.

**Two fixed chaos seeds.** The `network-e2e-chaos` job replays `send-chaos.test.ts` under two fixed seeds (one matrix leg each, proverless, retry 0) inside the lane's `status`, on Chrome and on Firefox, so a red seed blocks the merge like any suite; the nightly keeps hunting with a new seed each night. Each leg takes about 4-5 minutes, inside the lane's longest shard, but the four legs queue for the same runners as the lanes. A seed fixes the actions, not their timing, so a red seed is a real failure until shown otherwise: fixed, or proven a flake by replaying that seed (re-running the red leg replays it; locally, `NULO_E2E_CHAOS=1 NULO_E2E_CHAOS_SEED=<seed>`), never given a test retry, skipped or rotated to pass. Its json report is read back against `scripts/ci-cd/canary-expectations.json`, so a chaos test that skipped or never ran reds the job. **Rotation**: a seed is replaced only by a PR that names the nightly run it comes from (the run's log prints `[send-chaos] seed=…` and the actions it drew). The list lives in the lane's `network-e2e-chaos` matrix, each seed beside its run, so both PR lanes and `release.yml`'s opt-in run replay it with no copy; `scripts/ci-cd/verify-cert-run.sh` names each seed's job, a list the pins hold to the lane. A caller that hands a seed (the nightly) runs the lane's `chaos / sends` job instead, and the fixed pair skips. A change to the chaos file's `plan()`, `ACTIONS` or `DAPP_SHARE`, or to the burst fixture's amounts, maps both seeds to new actions: read the actions the PR's run logs then.

#### Presto in CI

Each native-required network-e2e lane (every prover-ON one but the nightly's advisory in-browser leg, and unless a rollback flag below is set) installs and starts the headless **`presto-server`** binary (from the [`alejoamiras/presto`](https://github.com/alejoamiras/presto) repo) before the suite runs. The wallet build is stamped with `VITE_NULO_PRESTO_REQUIRED=1` so [`chain-runtime.ts`](./packages/aztec-runtime/src/pxe/chain-runtime.ts) constructs `ProductionPxeFactory` in **required-mode** — proving traffic MUST hit presto-server natively, never silently fall back to in-browser WASM. Required mode is also the only place plaintext HTTP is representable: the headless server is HTTP-only (`127.0.0.1:59833`), so the factory derives `httpsOnly: false` from the mode; production always passes `httpsOnly: true`. Layered enforcement:

- **Layer 1** (workflow) — `/health` preflight gates the run on `bb_available == true`. Server missing or unhealthy → red.
- **Layer 2** (wallet) — `chain-runtime.ts` does an eager `checkPrestoStatus()` at PXE creation (the error names the SDK's `reason` and, for `secure-connection-unavailable`, its `diagnosis`) + installs an `onPhase` guard that throws on `fallback` / `denied` / `secure-connection-unavailable` / `version-mismatch`. This is the per-test authority.
- **Layer 3** (workflow) — post-test step counts `Received /prove request` and `Proving succeeded` lines in `/tmp/presto-server.log`, prints `PROVE_SUCCESS=<n>` and a step-summary table, and **fails a `canary*` lane** when there were zero successful native proofs. On soak/dispatch lanes (`shard_label: soak-N`) it only reports — the in-test assertion in `tx-sendTx-default` (`data-backend="presto"` + the exact subtitle, `Proving with Presto ✦`, keyed on the build stamp) is what a prover-ON soak enforces, and the soak's own read-back requires that test to have passed when the soak names it ([§ the soak](#extension-network-e2e-soakyml)).

**Production behavior.** `VITE_NULO_PRESTO_REQUIRED` is only set in `_extension-network-e2e.yml`, and [`_build-extension.yml`](./.github/workflows/_build-extension.yml) fails a production build whose bundle carries `NULO_PRESTO_REQUIRED_BUILD_STAMP`. Production builds prove over HTTPS only (Presto's desktop app serves `https://127.0.0.1:59834` once its Encrypted Connection setup is done) with the SDK's silent WASM fallback for users without Presto. The nightly's advisory `network-e2e-canary-wasm` leg proves the canary files on that fallback (§ `nightly.yml`).

**Rollback flags** (both require repo write access; PR authors cannot toggle):
- `vars.NULO_E2E_DISABLE_PRESTO=1` (Settings → Variables) — the emergency kill switch, affects all PR + dispatch runs until cleared.
- `workflow_dispatch` input `disable_presto: true` — single-run override for investigation.

**Origin gate.** The server denies non-localhost browser origins by default, and the wallet proves from `chrome-extension://<id>` — unknowable before Chrome loads the unpacked build — so the start step sets `PRESTO_ALLOW_ALL=1` on the **server process only** (never at job level). Safe on a loopback-only server on a single-tenant, ephemeral runner where fork PRs receive no secrets; never on a self-hosted runner. It bypasses Presto's per-origin approval prompt by design — that path is exercised by the manual Mac check, not CI.

**Release-metadata token.** Before downloading a `bb` version it has not cached, Presto looks up that release asset's published SHA-256 on the GitHub API and refuses to run an unverified prover. Anonymous callers share a 60-request-per-hour budget keyed to the source address, which Actions runners exhaust between themselves; the lookup then fails with `Cannot verify bb v<x>: no digest available from GitHub API` and the shard produces no proofs at all. The start step therefore passes the workflow's own `secrets.GITHUB_TOKEN` to the **server process only**, under a renamed variable so it does not reach the rest of the step. Read access to a public repository's releases is the whole requirement, so the default token is enough and a fork PR's read-only one works too. Presto refuses redirects on that request (alejoamiras/presto#46), so the credential reaches `api.github.com` and nowhere else. A cached version needs no lookup, so this matters on the first run after a `bb` bump or a cold cache. **The token needs `presto-server` ≥ 1.1.2** (CI pins 1.1.3): 1.1.1 sent the lookup with no `Authorization` header and ignored the variable, so the canary failed intermittently with the message above — each failed proof a failed test. A pin below that line makes the lookup anonymous again. When requests outnumber proofs, the assert step prints the server's WARN/ERROR lines in the job log and the step summary; the full log is in the `network-e2e-logs-<shard>` failure artifact (`e2e-testing` skill, flake ledger row 31).

**Coexistence.** Presto and the retired Aztec Accelerator desktop app share the wire protocol on the same port: a still-running Accelerator answers a Presto client and the wallet cannot tell them apart. Quit or uninstall Aztec Accelerator before installing Presto.

**Bumping presto-server**: update `version`, `expected_tarball_sha256` and `expected_sha256` in `.github/workflows/_extension-network-e2e.yml`'s `setup-presto-server` step together. Both hashes are computed locally from the release assets; the `.sha256` sidecar from the same release is a transfer-integrity check, not a security boundary. See [SECURITY.md](./SECURITY.md#binary-dependencies).

#### Proverless network e2e (the two-build split)

Most network-e2e files run against a **proverless** wallet build (`_extension-network-e2e.yml` input `proverless: true` → `NULO_E2E_PROVERLESS=1`): [`chain-runtime.ts`](./packages/aztec-runtime/src/pxe/chain-runtime.ts) sets `proverEnabled:false`, so the PXE skips BB-SNARK generation — kernel simulation + on-chain submission stay real, and the local node accepts the fake `ChonkProof.random()` proof. This makes the shard pool fast and CDP-stable. Presto is forced OFF for proverless jobs (`proverless` ⊥ `VITE_NULO_PRESTO_REQUIRED`).

A few **STUB** tests (`cancel-mid-prove`, `concurrent-sendtx-{approve,confirm}`) need a controllable prove window — proverless prove collapses to sub-second, too fast to observe sequencing/cancel. They run proverless and drive a `ProofGate` (a `chrome.storage.session` barrier, key `nulo:e2e:proof-gate`, injected into the **SW** `ExecutionCoordinator.proveTxTask` — the offscreen document has no `chrome.storage`) to hold the tx at `proving` deterministically, then release.

**Real BB proving stays covered** by the `network-e2e-canary` job (prover-ON, presto-server), on Chrome and on Firefox: `transfers` (wallet UI, waits through real prove → mine) + `tx-sendTx-default` (dApp, waits through real prove → submit — the node validates a real proof at `node.sendTx`; playground hard-codes `wait: "NO_WAIT"` so block-mine isn't awaited) + the two execution canaries (`frozen-account-canary`, `passkey-execution-canary` — the `@aztec` bump gate, CLAUDE.md "Account-address freeze") + `delete-after-prove` (a real prove, then the proving profile is deleted while the popup holds bb.js's CRS store open, as bb.js does once it loads the CRS). The job's `Assert canary results` step reads vitest's json report back against `scripts/ci-cd/canary-expectations.json`, so a listed file that never ran, a skipped test or a vanished canary is a red job.

**Production safety.** `NULO_E2E_PROVERLESS` is a **double-opt-in** build flag (`VITE_NULO_E2E_PROVERLESS` + `VITE_NULO_E2E_PROVERLESS_CONFIRM`; fail-closed throw if exactly one is set). The proverless branch + barrier are dead-code-eliminated from prod (referenced only inside `if (E2E_PROVERLESS)`); [`_build-extension.yml`](./.github/workflows/_build-extension.yml) asserts the build stamp + `nulo:e2e:proof-gate` key are ABSENT from every shipped `dist/{chrome,firefox}`. See [`implementations-plan/archive/e2e-proverless-stub/`](./implementations-plan/archive/e2e-proverless-stub/plan.md).

**The e2e wallet clocks.** The proverless build also sets `VITE_NULO_E2E_WALLET_CLOCKS=1`, a single build flag that shortens the incoming scanner's tick and the finality re-read to 10 s (`apps/extension/src/e2e/wallet-clocks.ts`); the prover-ON canary build passes `0` and keeps the users' 30 s and 60 s. The release env guard refuses the variable, and the same marker step refuses `NULO_E2E_WALLET_CLOCKS_BUILD_STAMP`; `scripts/ci-cd/build-env-guard.test.ts` runs that step against a bundle carrying each stamp the source defines.

### `pr-extension-smoke-e2e-firefox.yml` / `pr-extension-network-e2e-firefox.yml`

The two extension suites again, on Firefox. Each is a twin of its Chrome caller — same paths filter (re-pointed at its own file, plus `.github/actions/setup-geckodriver/**`), same labels, same shard / heavy / canary / chaos shape — calling the same reusable workflow with `browser: firefox`, which adds [`setup-geckodriver`](./.github/actions/setup-geckodriver/action.yml) (SHA-256-pinned tarball + binary), installs the e2e suite's pinned Firefox (`apps/extension/scripts/e2e/install-firefox.ts`, apart from Puppeteer's own revision; [`FIREFOX.md`](./apps/extension/tests/e2e/FIREFOX.md#which-firefox-the-suite-runs)), builds `dist/firefox` and runs the suite with `NULO_E2E_BROWSER=firefox`. Differences from the Chrome callers, all deliberate: `pull-requests: read` is granted to the `changes` job only, and two files skip their browser tests on Firefox (one kills the background under an open extension page, which Firefox declines; one redirects over CDP Fetch, which Firefox lacks; `CHROME_ONLY` in `apps/extension/tests/e2e/fixtures/browser/index.ts` carries each reason). The canary job runs the same five prover-ON files on both browsers — the two send specs, the two execution canaries and `delete-after-prove` — and its `Assert canary results` step reads vitest's json report back against `scripts/ci-cd/canary-expectations.json`, so a canary that skipped, vanished or never ran reds the job whatever the file count said; `behavior-gating.test.ts` pins every lane's lists, the prover-ON input, the pool partition, and that each aggregator reads every need through `toJSON(needs)`. Aggregators: `extension-smoke-e2e-firefox-status`, `extension-network-e2e-firefox-status`, the same exact-state shape.

**Required on `dev` and `main`.** The two PR aggregators (`extension-smoke-e2e-firefox-status`, `extension-network-e2e-firefox-status`) are required on both branches. Each passes when its lane is skipped (no matching paths, no label, and a base other than `main`); a draft runs its lanes like any other PR, on both browsers. `nightly.yml`'s Firefox jobs (`network-e2e*-firefox`, `smoke-firefox-against-artifact`) are in `publish-nightly`'s and `status`'s `needs`, so a red one publishes no nightly. In `release.yml`, `attach-assets` and `status` wait on its `smoke-firefox-against-artifact`, so a red one holds the release's assets. The lanes are not free: on a PR that trips both filters the two workflows start eighteen more jobs (fourteen suites, four control) that queue against the required lanes for the same runners, and `release.yml`'s Firefox smoke holds the `release` concurrency slot until it ends (a 45-minute execution timeout; time queued for a runner is on top), so it can also delay the *next* release. `scripts/ci-cd/behavior-gating.test.ts` pins the parity with the Chrome lanes (filters, file lists, retry, matrix), that in `release.yml` only `attach-assets` and `status` wait on a Firefox job, the `chrome` default of the shared `browser` input, and that the two browser caches share no key prefix, and that each Firefox gate triggers, decides and aggregates exactly as its Chrome twin's and no e2e lane, nor either gate script, reads the draft flag; `aggregators.test.ts` runs each lane's gate on a draft that touches its surface and fails it unless the suites run, and runs `nightly.yml`'s `status` script and pins `publish-nightly`'s whole condition. The switch table records both Firefox lanes as required on `main` ([`release` skill § Staged-rollout switches](./.claude/skills/release/SKILL.md#staged-rollout-switches)). How the suite drives Firefox and what differs: [`apps/extension/tests/e2e/FIREFOX.md`](./apps/extension/tests/e2e/FIREFOX.md).

### Check names and the protection runbook

Every aggregator check is named after the product it gates — `quality-status` (repo-wide), `extension-smoke-e2e-status`, `extension-network-e2e-status`, and the Firefox twins (required on `dev`) `extension-smoke-e2e-firefox-status` / `extension-network-e2e-firefox-status`. Branch protection matches those names literally, so a rename is a two-step owner action per branch, scripted in `scripts/ci-cd/required-checks.sh`: `print --branch <b> --json > <file>` (read-only; review the file), then `--apply --branch <b> --expect <file>` right before merging the rename (it refuses if the live protection drifted since the review, touches only `required_status_checks`, keeps `strict` and unrelated checks, verifies the write and prints the rollback). `--add a,b` appends new required checks the same way. `scripts/ci-cd/behavior-gating.test.ts` pins each PR workflow's aggregator name. The legacy labels `e2e:smoke` / `e2e:network` are still honored alongside `e2e:extension-smoke` / `e2e:extension-network` until the next stable cut.

### Concurrency

Each PR workflow (`pr-quick.yml`, `actionlint.yml` and the four e2e lanes) queues its runs per pull request and head commit, and only a `workflow_dispatch` cancels a run in flight, one of its own ref and commit. Runs of two heads never share a queue, so a run of an older push that GitHub admits late can neither cancel nor replace the current head's run. Runs of one head queue: one runs and at most one waits, and a later event of that head (a label, `ready_for_review`, `reopened`, a re-run) replaces the waiting run, which posts nothing; every run reads the live labels (below), so the survivor decides from state at least as new as the run it replaced.

A push leaves the old head's runs going, and `pr-supersede.yml` cancels them. On each `synchronize` of a same-repository pull request (forks and Dependabot hold read-only tokens and are skipped), its one job lists the branch's unfinished runs of those six workflows, then reads the pull request's head, and cancels each listed run that names this pull request and is on another head than its event's, re-reading the head before every cancel attempt. A sweep that reads any other head than its event's (newer, rewound, or a stale answer) stops without cancelling more, since every head change, a force-push rewind included, starts its own sweep; sweeps share no concurrency group, because GitHub may admit an older sweep last and a group would let it cancel the newer one. Cancellation is best effort: when sweeps are admitted out of order, an obsolete run can be left to finish. Listing first means no run of a push that lands after the listing is ever selected; listing in lifecycle order catches a run that moves on between two listings. Two residuals remain: a head change that lands between a re-read and its cancel call can still cancel a run of the head that becomes current, and a pull request endpoint that trails the run list while answering the event's head can let a later push's listed runs be cancelled. A cancelled run still runs its `always()` aggregator and posts FAILURE under its required name; on an obsolete head that is harmless, but on a head that becomes current again the rollup reads that FAILURE beside the new runs' results until the cancelled run is re-run. An e2e run that starts on an old head after the sweep stops itself in `Detect changes`; a late `pr-quick.yml` or `actionlint.yml` run finishes on its old head, deciding nothing for the current one. The job holds `actions: write`, runs no action, checks nothing out and reads every input through `env:`; `behavior-gating.test.ts` pins that, and `supersede.test.ts` runs its script under a scripted `gh`. The job prints each cancelled run and its API call count.

Every run evaluates its whole gate, whichever label started it, from the pull request as it is when its `Detect changes` job runs: `scripts/ci-cd/live-labels.sh` reads the live labels, base and head from the API, never from the event's snapshot, writes `label-hit` as `true` or `false` and the base (the job's last step, `Decide`, refuses anything else), and fails a run whose head the pull request has moved past (after one late read, since the endpoint can trail a push) before any suite starts. An API failure fails the job after one retry. A partial re-run ("Re-run failed jobs", or one job) carries the earlier attempt's gate over, so each lane's aggregator accepts skipped suites only when the labels were read in its own attempt: re-run all jobs to re-decide. The four lanes share both gate scripts: `Decide` runs `scripts/ci-cd/e2e-decide.sh`, and each `*-status` job checks out `scripts/ci-cd/e2e-aggregate.sh` alone (sparse, at the run's `github.sha`, no credential kept) and runs it on the job's `toJSON(needs)`, so a gate rule is one edit and every need is read. That checkout is a step a required check can now fail on: when GitHub's git service is down or slow, or no longer serves the run's merge commit to a late re-run, the status job goes red, never green without evaluating. Recover with "Re-run failed jobs" when the suites ran, "Re-run all jobs" when the lane skipped (a skip stands only on labels read in that attempt), and a push or a close and reopen when the merge commit is gone, since every re-run keeps its run's `github.sha`. A retarget starts no run of a lane (`edited` is not subscribed: every title or body edit would re-run the suites); `pr-retarget.yml` re-runs them instead (below). Do not skip a run whose label is irrelevant: its aggregator would report `skipped`, which branch protection accepts, and could green the required check before any run of that head had run its suites. The price is a second full run when a label lands, or a draft is marked ready, while a run is in flight (per browser, eleven suite jobs on a PR that trips the network filter and three more when it trips the smoke one).

A base change re-runs the four e2e lanes. `pr-retarget.yml` subscribes to `edited`, and its one job runs only when the event carries `changes.base`, on a same-repository pull request (a fork's or Dependabot's token could not re-run anything, so a fork's pull request keeps the manual recovery below). For each lane it lists the runs of the event's head for this pull request and takes the newest. A completed run gets "Re-run all jobs" at once: the new attempt's `Detect changes` reads the new base, and its aggregator accepts a skip read in that attempt. (A re-run keeps its run's workflow revision and event, so a run created before the lanes read their base live, on 2026-10-09, re-decides on its event's base; on `main` the up-to-date rule forces a push first, which starts fresh runs.) GitHub re-runs only a completed run, so a run in flight is cancelled, and the job reads every cancelled lane once per pass until each has completed, then re-runs it; an attempt above the one its cancel left counts as done, since another request started it after the listing. A title or body edit starts the workflow, which skips the job. The job is not a required check and cannot be one: it runs only on a base change, so every other pull request would wait on it at `Expected`. When it cannot re-run a lane (GitHub re-runs a run only within 30 days and at most 50 times; a cancelled run that has not completed when the job's 15 minutes run out; an API refusal after its retry), it goes red (its error names each lane it could not re-run; after a timeout, its `cancelled <id> <file>` lines do), and the lane keeps the check it earned on the old base: re-run all jobs of the failed `Retarget` run (its payload keeps the base change), push, or close and reopen the pull request. A cancel that lands after `Detect changes` skipped the suites still posts the skip's success, so there only the job's red shows the lane was not re-decided, and a later title edit's skipped `Retarget` run can hide that red in the rollup. When a stacked parent merges, GitHub retargets the child, so the job fires; the rebase push that follows supersedes what it re-ran. A head whose merge ref does not carry `pr-retarget.yml` (a branch cut before it landed, retargeted to `main` before the next promote) starts no job: close and reopen, or push. `behavior-gating.test.ts` pins the job's trigger, scope and lane list, and that no other workflow subscribes to `edited`; `retarget.test.ts` runs its script under a scripted `gh`. The job prints each run it re-ran.

### `actionlint.yml`

Runs when any `.github/workflows/**`, `.github/actions/**`, or shell script changes. Lints the workflow YAML and shellchecks the scripts. Cheap; gate. Its `Status` (not required) is exact like `quality-status`: a linter whose filter tripped must succeed, one whose filter did not must be skipped.

### `release.yml`

Two triggers in one workflow:

- **`push` to `main`** — runs `googleapis/release-please-action` (v5, SHA-pinned). release-please scans Conventional Commits since the last tag and opens or updates a Release PR titled `chore(main): release X.Y.Z`. The PR bumps `package.json` + appends to `CHANGELOG.md` + updates `.release-please-manifest.json`. The PR's commits are app-authenticated (verified) via `actions/create-github-app-token` (v3, SHA-pinned) using the `RELEASE_PLEASE_APP_ID` + `RELEASE_PLEASE_APP_PRIVATE_KEY` secrets of the `release-app` environment (deployment branches `main` and `dev`), which only the jobs that mint the App token declare. release-please runs with `skip-github-release: true`, so it never tags or creates a GitHub Release (its own publish path also aborts on its known bug), and after a Release PR merges `release_created` stays false. The **`auto-unstick`** job tags instead: when `release_created != 'true'` on a `push`, it detects the merged `autorelease: pending` Release PR whose merge commit is `github.sha`, creates the tag through the REST API with its own narrow App token (or finds the one an earlier attempt created) + relabels, and feeds `resolve` (`unstuck=true` + the tag) so the chain continues in the same run. It's on unless `vars.AUTO_UNSTICK_ENABLED` is `off`, `false` or `0` (unset is on; an unrecognised value is off, with a warning) — with it off the job no-ops and the manual unstick in the [`release` skill](./.claude/skills/release/SKILL.md) is the fallback. Once a release is unstuck (auto or manual), the same workflow continues: gates → build chrome + firefox → smoke against the Chrome and Firefox build artifacts (the trees `attach-assets` then zips) → `release-notes` (git-cliff, in a read-only job) → `attach-assets` (zip + SHASUMS, then `scripts/release/attach-assets-run.ts`: the GitHub Release is created as a draft, filled, read back by digest, attested, given the notes, published and read back again; a published release is never uploaded to) → the store uploads (opt-in inputs, see below). The landing is not part of the chain: it links the store listings, never a release, and Workers Builds redeploys the `nulo-landing` Worker on pushes to `main`. A stable push also runs **`sync-main-to-dev`** (advisory, push-only): it opens the `chore: sync main → dev` PR that carries the release bump + `CHANGELOG` back into `dev` and re-baselines the prerelease manifest — clean PRs await your merge commit (`gh pr merge <n> --merge`, never squash: `dev` must keep `main`'s release commit in its ancestry for the prerelease version anchor), conflicts are labeled `needs-manual-resolution` (see [`release` skill § After a stable cut](./.claude/skills/release/SKILL.md#after-a-stable-cut-promotes-to-main)).

- **`workflow_dispatch`** — finish the release of an existing tag, or submit a published one to the stores. Takes `tag` (e.g. `vX.Y.Z`), `dry_run` (default false), `run_network_e2e` (default false), `publish_chrome` and `publish_firefox` (both default false). Skips `release-please`; runs `resolve` → gates → build → smoke → `release-notes` → `attach-assets`. A release not yet published is published only by a run dispatched with `--ref <tag>`, so the attestation names the tagged commit; a published one is never uploaded to and never rebuilt: `select-assets` (read-only, `contents: read` and `attestations: read`, beside lint and unit) downloads its assets and checks each against its digest, its attestation for the tag's commit and `SHASUMS256.txt`, both builds skip, both smokes run the unpacked trees of those zips (`published-chrome`, `published-firefox`), and `attach-assets` checks the same bytes against the release once more before the store jobs get them. A dispatch on a release not yet published (or a draft) builds as a push does; a rebuild that meets a release published during the run ships only if it is byte-identical. A push is unchanged: `select-assets` skips, and a rerun of an already-published push run downloads and ships the published assets, a differing rebuild only a warning. A dry run follows the same choice, so it rehearses a store submission on the release's own bytes.

`attach-assets` runs only when every gate it waits on succeeded, the network suite ended exactly as `run_network_e2e` asked, `select-assets` ran exactly on a dispatch and wrote `build` or `published`, each build ran exactly when the source is this run's own, the notes job succeeded, and the run was not cancelled; the builds and smokes take the same `select-assets` clauses, so a dispatch whose selection failed runs none of them. It and `publish-nightly` hold `contents: write`, and the jobs that tag (`auto-unstick`) or open the sync PR hold an App token that can write; each of them installs no dependency, checks out the workflow's own revision without persisted credentials, sets `GH_TOKEN` per step and runs no third-party action but `oven-sh/setup-bun`, which gets no token (`scripts/ci-cd/release-integrity.test.ts` pins this and every App token's permission set). The `status` job checks every stage against its own condition and the control outputs those conditions read (`release_created`, `unstuck`, `is_prerelease`, `on_main`, `source`), so a stage that never ran, or a requested store upload that silently skipped, reds the release run.

**Store uploads** are opt-in `workflow_dispatch` inputs, never automatic: `gh workflow run release.yml --ref main -f tag=vX.Y.Z -f publish_chrome=true`. Both publish jobs gate on `always() && !cancelled()`, the input, `resolve` + `attach-assets` success, `is_prerelease == 'false'` and `resolve`'s `on_main` output (the tag's commit is an ancestor of `origin/main`: `--ref` authenticates the workflow file, not the tag it checks out). `publish-chrome-store` is **keyless**: `environment: chrome-web-store` (variables `CWS_WIF_PROVIDER`, `CWS_SERVICE_ACCOUNT`, `CWS_PUBLISHER_ID`, `CWS_ITEM_ID`, `CWS_PUBLISH_TYPE`; no secret), `permissions: id-token: write`, `google-github-actions/auth` exchanges the job's OIDC token through Google Workload Identity Federation for a ten-minute access token on the service account linked in the Chrome Web Store dashboard, and `scripts/release/publish-chrome-store-run.ts` verifies the zip's checksum line, preflights `fetchStatus`, uploads, polls if the upload is async and publishes with `blockOnWarnings: true`. When the store refuses on warnings whose every `reason` is on the script's accepted list (`ACCEPTED_WARNINGS` in `publish-chrome-store.ts`: `BROAD_HOST_USAGE`, raised by the content script matching every page), it records the decision in the job summary and as a workflow warning, then retries once with `blockOnWarnings: false`; any other warning, an unreadable refusal, or a retry whose response lists a warning outside the list fails the job (the submission then exists, for the owner to review or cancel in the dashboard — the script never cancels one). Growing the list is a reviewed code change, not a variable, and `apps/extension/src/manifest.test.ts` pins the host permissions, the content-script matches and the absence of optional grants so nothing widens behind the accepted warning. A `dry_run=true` dispatch verifies the zip and prints the plan without authenticating. `publish-firefox-amo` runs in `environment: firefox-add-ons` with `contents: read` only; the Mozilla API key pair (`AMO_JWT_ISSUER`, `AMO_JWT_SECRET`) reaches exactly one step, after every third-party action has run. `scripts/release/publish-firefox-amo-run.ts` verifies the Firefox zip's checksum line, refuses a Chrome zip, a foreign `gecko.id` or a data declaration other than the settled `["financialAndPaymentInfo"]`, requires the `git archive` source package (prefixed `nulo-<v>/`, with `SOURCE-BUILD.md` and `bun.lock`, under 200 MB) and the reviewer-notes block of `apps/extension/store/listing.md`, then uploads on the listed channel, polls AMO's validation (five-minute deadline; `valid: false` prints the errors and creates nothing), creates the version with those notes and attaches the source. Every request carries a fresh 60-second HS256 JWT, masked. A failure after the version exists prints the recovery procedure (never re-run; attach the source by hand or re-send the `PATCH`). **`store-check.yml`** (`workflow_dispatch`, input `store` = `chrome` | `firefox` | `both`) proves a store credential read-only — Chrome: one `fetchStatus`; Firefox: the author-scoped add-on list must contain `wallet@nulo.sh` — in the store's environment, no upload, and is deliberately not an input of `release.yml`, whose non-dry dispatch publishes or re-verifies the release and rewrites its notes. **`verify-store-copies.yml`** (weekly, or `-f store=chrome|firefox|both`) checks the other end: it downloads each store's public copy (no credential, no environment; the job token reads only), verifies the release zip that copy's `version_name` names through `attach-assets-run.ts`'s own `fetchVerified` (digest and attestation; `SHASUMS256.txt` likewise), and compares them file for file with `scripts/release/store-copy.ts`, which allows each store only its exact additions. Reproducibility of the Firefox source package is checked by `source-rebuild.yml` (weekly, or `-f tag=vX.Y.Z`): `git archive` rebuilt on x86_64 and Ubuntu ARM64 must be byte-identical to the shipped zip.

**Artifact handoffs go by id.** Any job of a run holds the artifact token and can replace an artifact under its name, so every artifact an extension smoke or a release or nightly publisher takes is downloaded by the id its producer's upload returned: the builds' `chrome_artifact_id` / `firefox_artifact_id` (`_build-extension.yml` outputs), `select-assets`' published trees and assets, each notes job's notes, and `attach-assets`' `release-${VERSION}` (`release_artifact_id`, which both store jobs take). `_extension-smoke-e2e.yml` takes the id as `artifact_id` beside `artifact_name`. A download by id fails when the artifact under that id is gone or replaced, and checks the archive against the digest the service recorded at upload; a step before each download refuses an id that is not a positive integer, because an empty one downloads every artifact of the run. `scripts/ci-cd/artifact-handoffs.test.ts` pins each consumer to its producer's upload.

Config files: `.github/release-please-config.json`, `.release-please-manifest.json`, `CHANGELOG.md`. The git-cliff template at `cliff.toml` provides the final release-body content.

### `nightly.yml`

The repo's only nightly workflow (`source-rebuild.yml` runs weekly): every night it builds current `dev` and publishes a **prerelease** GitHub Release (`v<version>-nightly.<YYDDD>`) with the chrome + firefox zips + SHASUMS256.txt, so people can install the latest state of dev without a maintainer hand-off. Nightlies are marked pre-release and never take the "Latest" badge from stable releases. Also dispatchable manually (`force` bypasses the quiet-day skip; `dry_run` runs all gates but skips the publish).

- **Version scheme**: `<dev package.json version>-nightly.<YY+day-of-year>`. Chrome/Firefox cap each manifest version component at 65535 and `manifest.config.ts` strips non-numerics, so a calendar date would overflow — YYDDD keeps every component valid while `version_name` shows the full string. A nightly takes today's code, or one past the newest nightly code on any version line when that is later (a same-day re-run), never a `.1` suffix (a fifth component is an invalid manifest); so no name `prune-nightlies` freed is cut again, and tonight's nightly is always the newest.
- **Gates are hard**: lint+typecheck → unit → full network suite (the PR gate's lane: 5 proverless shards + 3 heavy jobs + real-proving canary, with the run's own `send-chaos` seed in place of the fixed pair), on Chrome and on Firefox → chrome+firefox builds with the nightly version override → smoke against each built artifact. The tag + release are created only after every one of those gates is green, so a failed gate publishes nothing; only `dup-trend`, `rp-host-live`, `network-e2e-canary-wasm`, `token-list-host-live` and `seed-identity-live` gate nothing. `aggregators.test.ts` holds `status` to every job but those five, refuses any job that waits on one of them, runs its script, and pins `publish-nightly`'s whole condition.
- **In-browser proving (advisory)**: `network-e2e-canary-wasm` runs the canary's five files with `disable_presto: true`, so the wallet proves in browser WASM, the path of every user without Presto, which every other prover-ON job normally replaces with native proving. Its json report is read back like the canary's. No job needs it: a red leg reds the run, not `status` or the publish. Making it a gate is the owner's call after 30 consecutive green nights ([`release` skill § Staged-rollout switches](./.claude/skills/release/SKILL.md#staged-rollout-switches)). It adds one runner for about ten minutes a night (one measured run: 9 min 39 s, against about 7.5 for the native canary).
- **Flake policy** differs deliberately from the PR gate: the network suite runs at its config-default retry 2 (the PR gate forces 0 for honesty) plus the built-in infra-boot retry. A nightly absorbs flakes; a PR must surface them. The chaos file pins its own retry 0, so the nightly never retries it: a retry would replay a burst against balances the first attempt moved.
- **A red chaos night** publishes nothing. Its seed is in the log (`[send-chaos] seed=…`), and a `chaos_seed` dispatch replays it; an unseeded run takes the run id, which "Re-run failed jobs" keeps, so a re-run replays the same actions (a seed fixes the actions, not their timing). A red seed is a bug, filed as an issue with that seed; a later green night does not clear it.
- **Retention**: `prune-nightlies` runs after a successful `publish-nightly` in the same run, so the two never race, and keeps the newest fourteen nightly names over tags and releases together (`scripts/release/prune-nightlies.ts`: `v<x.y.z>-nightly.<YYDDD>` only, ordered by date code, then version). It deletes each older one's releases, drafts included, then its tag, re-reading each before and after, and stops at the first refusal; on a `dry_run` it only lists them. A quiet day runs no prune, so a prune cut short is finished by the next published night. It holds `contents: write` alone and relies on the owner's exclusion of nightly tags from the `release tags` rulesets ([`release` skill § Tag rulesets](./.claude/skills/release/SKILL.md#tag-rulesets-and-immutable-releases)). `release-integrity.test.ts` pins its token, its checkout, its guard and its dry-run switch, and that no other job prunes; `nightly-resolve.test.ts` pins the code `resolve` cuts.
- **Quiet-day skip**: if a `v*-nightly.*` tag at dev HEAD has a published release, the run no-ops green. A tag without one does not count.
- **Stable notes are protected**: `release.yml` picks the notes range by commit history, not by tag order. `git describe` takes the nearest `v[0-9]*` tag reachable from the release commit's parent, skipping `-nightly` and `-internal` tags (and `-rc` tags for a stable release), and git-cliff renders exactly that commit range with only the release's own tag visible (`--tag-pattern`), keeping commits that touch `apps/extension/**`. So a stable covers everything since the previous stable, an rc everything since the previous rc or stable, and no nightly tag can cut either short. The nightly's own notes run `--unreleased`, so they start at the newest earlier tag, normally the previous nightly — a daily delta.
- **Publishing**: `publish-nightly` runs the same `scripts/release/attach-assets-run.ts` as `release.yml`: it creates the nightly's tag at the built commit (refusing one already elsewhere), fills a draft prerelease, reads it back by digest, attests it and publishes it. `resolve` builds the run's own commit and refuses any ref but `dev`, so the attested commit is the tagged one.
- **Interrupted-publish recovery**: a cancelled publish leaves the tag and at most an unpublished draft. Re-run the failed `publish-nightly` job (it finishes the draft), or let the next run publish under a fresh date-code tag. The leftover tag and draft stay until `prune-nightlies` deletes them with the other nightlies past the newest fourteen.
- Schedules fire from the workflow file on the default branch (`dev`) — the trigger is inert on feature branches until merged.

### `extension-network-e2e-soak.yml`

The branch-level flake check, and the only instrument that repeats: a manual dispatch runs the named network test files `repeats` times (1 to 25) in sequence, each iteration one job of `_extension-network-e2e.yml` on Chrome, at `retry: "0"` by default and `fail-fast: false`, so a test that passes only on a retry fails its iteration and every iteration reports. `gh workflow run extension-network-e2e-soak.yml --ref <branch> -f test_files="tests/e2e/network/<name>.test.ts" -f repeats=5`.

- **Name the files.** `test_files` takes `tests/e2e/network/<name>.test.ts` paths and `tests/e2e/egress-guard.test.ts`, space- or newline-separated: the file a fix touches, or the files of a red shard (its job log lists them as vitest ran them) less the ones below that cannot soak green. The list must fit one 30-minute job.
- **A blank list starts no run**: `test_files` is required, and GitHub refuses an empty or whitespace-only value at dispatch (HTTP 422). **`prep` refuses** before any runner builds: a token that is not such a path (an option, a directory, a glob, `..`, a smoke file) or names no file at the dispatched commit; `repeats` outside 1 to 25; `retry` other than empty or one digit. vitest reads each name as a case-insensitive substring filter and ORs them, so without the check a typo beside a real path would be dropped silently.
- **Every named test must run.** Each iteration writes vitest's json report, and `Assert soak results` reads it back with `scripts/ci-cd/assert-canary-results.ts --allow-unlisted`: every named file present, every test in it passed, and a file `canary-expectations.json` lists keeps its titles. A skipped test reds the iteration, so a file whose tests run only when armed cannot soak green: `send-chaos` (its seeds replay in the lane's chaos jobs) and the opt-ins `_probe-warmup-effect`, `update-in-place`, `store-captures`, `stale-anchor-recovery` and `stale-network-a10-capture`. Nor can a file with a browser- or CI-gated test, such as `firefox-background-restart`, `window-placement` or `import-handshake-note-matrix` ([#1018](https://github.com/nulo-sh/nulo/issues/1018), a known limit).
- **`Status`** is green only when `prep` and every iteration succeeded. It states the count, and "zero test retries" only at `retry=0`; the suite's one infra-boot retry on exit 86 reruns no test.
- **The build.** `proverless` (on by default) builds the proverless wallet; off, the wallet proves for real through Presto unless `disable_presto` is set. Under `proverless=false`, `proverless-guard.sh` refuses a `@requires-proverless` file at each iteration's start.
- **Runs.** A second dispatch on the same ref cancels the first. Each iteration checks out the branch when it starts, so do not push to it mid-soak ([#977](https://github.com/nulo-sh/nulo/issues/977)). Chrome only: the soak has no `browser` input.
- **The whole suite is not a soak.** It does not fit one job. A whole-suite run at retry 0 on a branch is a dispatch of `pr-extension-network-e2e.yml` and of `pr-extension-network-e2e-firefox.yml` (`gh workflow run <file> --ref <branch>`), each the full lane once, or a green PR run of both. `nightly.yml` builds `dev` only, at the config-default retries, so it is never a branch soak.

### `publish-packages.yml`

Manual only (`version`, `dry_run` default true; refuses any ref but `dev`/`main`). Publishes `@nulo-sh/wallet-crypto`, `@nulo-sh/resolve-asset` and `@nulo-sh/wallet-sdk-schema-patch` at one lockstep version through npm trusted publishing — no npm token exists. Four jobs. `test` runs `test:release` (it executes `@aztec-labs/*` code, so it makes no bytes). `pack`, in parallel, makes the bytes and runs no test code: `oven-sh/setup-bun` with its cache off and a fresh `BUN_INSTALL_CACHE_DIR`, `bun install --frozen-lockfile --ignore-scripts` (a shared Actions cache is writable by any dev- or main-scoped job, so none is restored), `scripts/publish/stage.ts --all` → `npm pack` of every staged directory → `check-digests.ts` (the first publication, `0.1.0`, must match `scripts/publish/approved-digests.json`) → the tarballs as an artifact, with their sha256 and integrity in the step summary. `publish` needs both, is the only job with `id-token: write`, runs in the `npm-publish` environment (owner approval) and runs no repository code: it checks the tarball set against the three names, re-checks the digests on the downloaded bytes, refuses any version but `0.1.0` until `0.1.0` is on npm, skips a version already published with identical bytes, and runs `npm publish --provenance`. `verify` then waits, for up to 15 minutes, until the registry's document lists every version and every tarball URL answers 200 (a fresh version can take minutes to reach the registry's CDN), and runs `scripts/publish/verify-provenance.sh` on each tarball (`gh attestation verify` against the registry's SLSA bundle: signed by this workflow on `dev` or `main`, naming these bytes) and `npm audit signatures`, which also covers a skipped re-run. `publish` and `verify` download `pack`'s artifact by ID and check each tarball against the sha256 list `pack` outputs, because `test` holds the same artifact token and could replace a named artifact. Node is pinned exactly because the digests depend on its npm and zlib. `scripts/ci-cd/publish-packages.test.ts` pins that shape; [`scripts/publish/README.md`](./scripts/publish/README.md) has the one-time trusted-publisher bootstrap.

### `publish-token-list.yml`

Runs on a push to `dev` that changes `infra/token-list/list.source.json`, and on a dispatch from `dev`; one run at a time, never cancelled. Three jobs. `prepare` holds no secret: it runs the tree invariants (`bun run --cwd infra/token-list check`) and writes the review summary (the token diff against the served envelope, the tokens sha256, and the signing-relevant changes it lists since the last publish, a list the candidate revision produces and so informational only: GitHub's compare view of the range is the authoritative review), whose digest becomes its output; then an advisory step (`continue-on-error`, 5 min) appends the live check, each entry's instance, class, symbol and decimals read from the keyless public node `https://aztec-testnet.drpc.org`; no failure of it blocks `sign`, which it delays by at most those 5 min. `sign` runs in the `token-list` environment (owner reviewer, branch `dev`), checks out without credentials, installs nothing, and runs `bun --no-install packages/token-list/src/sign-cli.ts` with `TOKEN_LIST_SIGNING_KEY` in that one step; the signer refuses any token set but the summary's digest, a sequence (the signing time in seconds) not above the served one, and a key that is not the pinned `nulo-ci-1`, and verifies its own output. `publish-pr` runs in the `release-app` environment and mints the release App token (contents and pull-requests write), commits the envelope to `infra/token-list/public/v1/list.json` on `token-list-publish-<sequence>` through `createCommitOnBranch`, opens the PR into `dev` and closes older publish PRs; that PR's `quality-status` re-verifies the envelope, and the owner merges it, which Workers Builds deploys to `tokens.nulo.sh`. `release-integrity.test.ts` and `behavior-gating.test.ts` pin the jobs and the commands; nightly's advisory `token-list-host-live` probes the served list. Runbook: [`infra/token-list/README.md`](./infra/token-list/README.md).

## Releasing

Releases are driven by `release-please`. The human touchpoint is a single click — merging the Release PR.

1. Confirm what you want to ship is on `main` (via the usual `release: promote dev → main` PR).
2. Wait for `release.yml` to run on the push to main. It opens (or updates) a Release PR titled `chore(main): release X.Y.Z`. The version comes from Conventional Commits since the last tag.
3. Review the Release PR. CI runs the normal `quality-status` check. Eyeball the proposed `CHANGELOG.md` diff + `package.json` bumps.
4. Merge the Release PR via the GitHub UI (merge commit).
5. The merge's push-to-main run of `release.yml` tags the release: release-please never tags, so `auto-unstick` creates the tag unless `AUTO_UNSTICK_ENABLED` turns it off (see § `release.yml`). The same workflow run continues: gates → build chrome + firefox → smoke both builds → git-cliff notes → `attach-assets` (creates the GitHub Release as a draft, uploads and checks the zips + SHASUMS, attests them, adds the notes, publishes it).

Tag format is `v<X.Y.Z>` (forced by `include-v-in-tag: true` + `include-component-in-tag: false` in `.github/release-please-config.json`). Prerelease (rc) support **exists** — `v<X.Y.Z>-rc.<N>` cut from `dev` via [`release-prerelease.yml`](./.github/workflows/release-prerelease.yml); see the [`release` skill](./.claude/skills/release/SKILL.md) § Prerelease (rc) from `dev`.

### Forcing the next-version

release-please picks the next version from Conventional Commit types: `feat:` → minor, `fix:` → patch, `BREAKING CHANGE:` (in the body or footer) → major, except that while the version is `0.x` `bump-minor-pre-major: true` makes it a minor. To force a specific version mid-flight, add a `Release-As: X.Y.Z` footer to any commit on `main`.

### Finishing the release of an existing tag

If a release was tagged but its publish failed or was cancelled (the tag has a draft or no release), use the `workflow_dispatch` escape hatch, from the tag:

1. `gh workflow run release.yml --ref vX.Y.Z -f tag=vX.Y.Z` (in the Actions tab: "Run workflow", "Use workflow from" the tag). A run from any other ref refuses to publish, because the attestation must name the tagged commit.
2. The inputs:
   - `tag` — e.g. `vX.Y.Z`. Required.
   - `dry_run` — leave **false** to publish; `true` builds and plans without touching the release.
   - `run_network_e2e` — defaults to **false**; set it true to run the network suite before the publish.
   - `publish_chrome` / `publish_firefox` — leave **false**: the store submission is a separate dispatch from `main` once the release is published (its environments allow `main` only).
3. The workflow skips `release-please`, fetches the tag, and re-runs gates → build → smoke → notes → `attach-assets`, which finishes the draft.

## Debugging a failing PR

1. Click the failing check in the PR conversation. The `status` aggregator job's first error line points at the underlying job.
2. Open the underlying job's log. Failures are surfaced via `::error::` annotations and tend to surface as a single line.
3. Match against the workflow source (`.github/workflows/...`) to confirm what step ran.
4. Re-run the failing job from the GitHub UI ("Re-run failed jobs") if you suspect a transient flake.

For smoke / network e2e specifically: failure artifacts (vitest output, `.e2e-state/`, sandbox logs) upload on failure. Download them from the run page's "Artifacts" section.

## CI gating — derived from the dependency graph

The `pr-quick` / `pr-extension-smoke-e2e` / `pr-extension-network-e2e` `changes` jobs use `dorny/paths-filter` to skip work on PRs that can't affect a given target. **These filters are derived from the workspace dependency graph, not hand-curated** — a suite/build runs whenever any package its target is built from changes:

- **Built targets** (`extension`, `landing`, `playground`) → gated on the **whole package** (`apps/<target>/**`), so no build input (manifest, vite/tsconfig configs, `public/` assets, scripts, the e2e harness) can ever be silently missed.
- **Dependency libraries** (`wallet-core`, `wallet-crypto`, `extension-messaging`, `aztec-runtime`, `wallet-bridge`, `design`, `legal`, `resolve-asset`, `third-party-notices`, `wallet-sdk-schema-patch`) → gated on their consumed surface (`packages/<dep>/src/**` + `package.json`); their own README/docs stay out of the gate.
- Plus repo-wide build inputs (`package.json`, `bun.lock`, `bunfig.toml`, `tsconfig.json`, **`patches/**`**) + each suite's harness/workflow files.

**Two hard rules:**

1. **Never use a bare `!` negation pattern.** `dorny/paths-filter` defaults to `predicate-quantifier: some` (a file matches a filter if it matches ANY pattern), so a bare `!packages/x/**/*.md` matches *every file that isn't that md* → the filter silently becomes `**` and fires on every PR. Exclude by listing positive paths only (or, for true subset-exclusion, picomatch extglobs — never a bare `!`).
2. **Gate on the graph.** When the extension or the landing gains a new `@nulo/*` dependency, add it to the relevant filters. [`scripts/ci-cd/behavior-gating.test.ts`](./scripts/ci-cd/behavior-gating.test.ts) recomputes each target's transitive graph from `package.json` and **fails CI** (via the `test:ci-gating` step in `_unit-tests.yml`) if a gate doesn't cover it, or if a `!` negation reappears — so the lists can't silently rot. The gates intentionally **over-trigger** (a colocated `*.test.ts`/`*.stories.ts` edit under `src/` runs the e2e suites) — the safe direction: err toward running, never skipping.

Design record: [`implementations-plan/archive/paths-filter-negation-fix/`](./implementations-plan/archive/paths-filter-negation-fix/plan.md).

## Adding a new gate

1. If the gate is a single shell step, add it to an existing workflow's job.
2. If the gate is a whole job with its own runner / timeout / failure-artifact policy, create a reusable workflow at `.github/workflows/_<gate-name>.yml` and call it from the relevant top-level workflow(s).
3. Add it to the `status` aggregator's `needs:` and check its result there against the state its `if:` asks for (`success` when it runs, `skipped` when it does not); in an e2e lane, `needs:` is the whole change, since `scripts/ci-cd/e2e-aggregate.sh` holds every need but `changes` to that rule. [`scripts/ci-cd/aggregators.test.ts`](./scripts/ci-cd/aggregators.test.ts) and `behavior-gating.test.ts` fail on a need the aggregator never checks.
4. Update this file's "What runs when" matrix.

The reusables today are:
- `_lint-and-typecheck.yml` — biome + typecheck
- `_unit-tests.yml` — vitest workspace-wide
- `_build-extension.yml` — chrome + firefox (with optional version override)
- `_extension-smoke-e2e.yml` — puppeteer smoke against `EXTENSION_PATH` or downloaded artifact
- `_extension-network-e2e.yml` — the `network suite` job: Aztec sandbox + the local `e2e:agent` runner, one job per shard or dedicated file list
- `_release-pr-lockfile.yml` — writes the Release PR's version into `bun.lock` (advisory)

Composite actions (step-level reuse):
- `setup-bun` — bun + install cache (`cache: "false"` skips it) + `bun install --frozen-lockfile`; the caller checks out first
- `setup-aztec` — Foundry + Aztec CLI matching the declared version, cached; the installer script, its `versions` manifest and the noir and Foundry tarballs are SHA-256-pinned (`installer-pins.sha256`), and the CLI's npm tree is installed from a committed lockfile with install scripts off
- `setup-puppeteer` — `~/.cache/puppeteer` cache
- `setup-geckodriver` — SHA-256-pinned `geckodriver` for the Firefox lanes
- `setup-presto-server` — SHA-256-pinned headless `presto-server` for the prover-ON network lanes

## Known limitations

- **Extension smoke e2e is required on both `dev` and `main`** (as `extension-smoke-e2e-status`). Its fixtures can still flake (cross-file Chrome teardown — see [`implementations-plan/archive/ci-cd/plan.md`](./implementations-plan/archive/ci-cd/plan.md#smoke-gating)); treat a red smoke like any gate — flake → re-run, breakage → fix — never neutralize it.
- **Extension network e2e quarantines nothing.** Every skip in `tests/e2e/network/` is a `skipIf` on the test's own precondition, such as an Aztec config, a local network or a behaviour only one browser has (`CHROME_ONLY` and `FIREFOX_ONLY` in `apps/extension/tests/e2e/fixtures/browser/index.ts` carry each browser reason). Open flake fingerprints live in the `e2e-testing` skill's flake ledger.
- **Store publishing**: both jobs need their GitHub environments (`chrome-web-store`, `firefox-add-ons`: reviewer = owner, `main` only) and an existing item on each store (see § `release.yml`). Nulo V6 reuses both items, renamed. The Firefox `gecko.id`, `wallet@nulo.sh`, is final.
