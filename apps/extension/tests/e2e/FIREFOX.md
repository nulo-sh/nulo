# Firefox in the e2e suite

What is different about driving the wallet on Firefox, why each difference exists, and where the suite absorbs it. Read this before touching `fixtures/browser/` or debugging a test that is red on Firefox only.

Run it: `NULO_E2E_BROWSER=firefox bun run e2e:agent …` (network; builds `dist/firefox` itself) or `NULO_E2E_BROWSER=firefox bun run test:e2e` (smoke). **Smoke does not build**: it loads whatever `apps/extension/dist/firefox` holds, so build first with the flags CI's smoke job uses — `VITE_NULO_E2E_MIGRATION_FIXTURE=1 VITE_NULO_E2E_TOKEN_SEEDS=1 VITE_NULO_E2E_TOKEN_SEEDS_CONFIRM=1 VITE_NULO_E2E_CSP_REPORT=1 bun run --cwd apps/extension build:firefox` — and run with `NULO_E2E_MIGRATION_FIXTURE=1 NULO_E2E_CSP_REPORT=1` (`_extension-smoke-e2e.yml` is the authority for both). Needs `geckodriver` on `PATH` or at `$GECKODRIVER`, and the suite's pinned Firefox (§ [Which Firefox the suite runs](#which-firefox-the-suite-runs)): `bun scripts/e2e/install-firefox.ts` from `apps/extension` (or `FIREFOX_PATH`). The driver runs exactly that revision — the Puppeteer cache is shared by every checkout on the host, so "newest installed" would let another worktree change this one's browser — and the launch fails below Firefox 153, the manifest's own floor. **Linux only**: launch ownership reads `/proc/<pid>/environ`.

## The one rule

**A browser difference lives on `BrowserDriver` (`fixtures/browser/index.ts`), never in a fixture or helper.** Tests may read `isFirefox` to skip a whole file (`describe.skipIf(isFirefox)(CHROME_ONLY.<reason>, …)`), to keep a test that needs a state headless Chrome cannot be driven into off Chrome (`describe.skipIf(!isFirefox)(FIREFOX_ONLY.<reason>, …)`), or to state a real behavioural difference in an expectation. `scripts/e2e/browser-seam.test.ts` enforces the rest: no scheme literal, no direct `browser.close()` / `newPage()` / `waitForTarget()`, no browser test — `isFirefox`, `BROWSER`, `driver.kind`, `NULO_E2E_BROWSER`, however imported — in `fixtures/**` or `helpers/**`.

A fix that reads "on Firefox, also do X" inside a helper is a second, unlisted driver. Put X on the interface, give Chrome its (often empty) implementation, and say why in the doc comment.

The one bounded exception is a browser surface the suite drives on Firefox alone, the toolbar panel and the sidebar, where the behaviour under test is Firefox's own: each is driven by a module of its own under `fixtures/browser/` (`firefox-action-popup.ts`, `firefox-sidebar.ts`), imported only by `FIREFOX_ONLY` specs. There is no Chrome implementation to give, so nothing goes on the interface.

## How Firefox is driven

Puppeteer speaks WebDriver BiDi to Firefox, and BiDi alone is not enough: it has no WebAuthn module, no window handles, and it cannot navigate to `moz-extension://`. So one browser is driven over **two channels on one session**:

- **geckodriver (WebDriver classic, HTTP)** owns the session: it launches Firefox, installs the add-on, navigates and reloads extension pages, adds the virtual authenticator, lists window handles.
- **Puppeteer over BiDi** attaches to that same session for everything else. `puppeteer.connect` insists on sending `session.new`, which Firefox refuses while the classic session holds the only slot, so `bidi-attach.ts` answers `session.new` / `session.end` locally and forwards the rest untouched.

Both geckodriver ports come from `reservePort` (`scripts/e2e/resolve-ports.ts`), which skips every port the host registry lists and never draws one of Fetch's bad ports, which browsers and undici's fetch refuse before connecting. `bidi-attach.ts` opens the BiDi socket with `ws` and the options of Puppeteer's own BiDi transport: Node's built-in WebSocket has lost that connection on a CI runner with no close frame from either end while Firefox stayed up (the `e2e-testing` skill's troubleshooting row 57).

A classic window handle and a BiDi browsing-context id are the same string in Firefox, which is what lets a Puppeteer `Page` be addressed on the classic channel. The id is read from Puppeteer's internal `Frame._id` (`contextIdOf` in `firefox.ts`); it throws by name if a Puppeteer upgrade moves it. **A Puppeteer bump is the one routine change that can break the Firefox driver wholesale** — run the Firefox smoke on it.

`--allow-system-access` is passed to geckodriver because Firefox otherwise refuses remote navigation to `moz-extension://` on both channels. It lets the automation session reach privileged contexts; acceptable on a single-user dev host and a single-tenant CI runner, and nowhere else.

## Which Firefox the suite runs

One pin: `E2E_FIREFOX_REVISION` in `fixtures/browser/firefox-revision.ts`. It is set apart from the revision Puppeteer pins, and everything reads it:

- the driver launches it, unless `FIREFOX_PATH` overrides;
- `bun scripts/e2e/install-firefox.ts`, run from `apps/extension`, installs it into Puppeteer's cache through the installed launcher;
- CI's `setup-puppeteer` action runs that script and keys its Firefox cache on the pin's file.

It holds stable_158.0. From Firefox 157, the Remote Agent treats a page in the `extension` process as a privileged context, and every wallet page is an extension page. On such a page, each BiDi command that does not opt in to privileged scope throws "The command does not support browsing contexts in privileged scope", even under `--allow-system-access` (`_getNavigable` in `webdriver-bidi/modules/RootBiDiModule.sys.mjs`). On 158.0 those include `browsingContext.activate`, `setViewport`, `captureScreenshot` and `print`, `input.setFiles`, the page-scoped `network` commands, `addIntercept` among them, and a page-scoped `script.addPreloadScript`. `script.evaluate` and `callFunction`, `input.performActions`, `browsingContext.getTree` and `locateNodes`, and `navigate` and `reload` pass.

Puppeteer's `page.bringToFront()`, `page.setViewport()`, `ElementHandle.uploadFile()` (`input.setFiles`) and `page.setRequestInterception()` (a page-scoped `network.addIntercept`) are among them, so no spec calls them: `bringToFront`, `setViewport`, `viewportOf`, `pickFile` and `answerRequests` are driver methods, and the seam test fails a direct call.

- `bringToFront` is Marionette's own window switch on the classic channel, which selects the tab and focuses its window, in turn with every other switch.
- `setViewport` runs the body of Firefox's own `setViewport` in Firefox's scope: the tab's `<browser>` takes the size, or with `null` loses it and so takes its window's, and the call resolves once the page reads the size. It goes over BiDi `script.callFunction` on one of Firefox's own windows (`browsingContext.getTree` with `moz:scope: "chrome"`), because `chromeScript`'s window switch would take focus from the page holding it. Firefox's resize has no `deviceScaleFactor`, `isMobile`, `isLandscape` or `hasTouch`, so the driver refuses each by name; only Chrome-only captures pass one.
- `viewportOf` is the driver's record of the last size it set, a reset's `null` included, since Puppeteer's `viewport()` never hears of that resize; a page the driver never sized reads Puppeteer's.
- `pickFile` answers the launch's file picker stand-in (`firefox-file-picker.ts`), so no BiDi `setFiles` is needed. Each launch registers, from a system-principal sandbox, a factory for `@mozilla.org/filepicker;1` in place of the native picker. A pick nobody asked for is cancelled at once, as a person closing the chooser does. The pick `pickFile` arms for its page's `browserId` is held, its input still in the page for `expectPickerLists`, until the driver answers it with the file, which fires `input` and `change`.
- `answerRequests` arms one `http-on-before-connect` observer in Firefox's scope (`firefox-answer-requests.ts`, over the same `script.callFunction` as `setViewport`). It matches the page's exact URLs on its tab's `browserId`, as DevTools filters a tab, and answers each with a response override or a refused connection before any connection, or TLS handshake, starts. Its `hits` reject on an answer that threw, whose channel is cancelled, and once the arm is gone. Puppeteer never hears an answered request finish, since only BiDi's own override reports a response, so each one stays in Puppeteer's in-flight count.

Before the pin moved to 158.0 ([#1111](https://github.com/nulo-sh/nulo/issues/1111)), one full smoke run there failed 35 of the 276 tests it ran, on three causes: the file pick and the page's request interception above, and the manifest's `sandbox: null` (the table below). A fourth, a fractional scroll end, showed once the flows after a pick ran (the table below). Two refusals stay unabsorbed, neither in a gate: a page screenshot (`captureScreenshot`) of an extension page, so `shotSend` and the chaos session's `screenshot` verb are Chrome-only, and the chaos session's page-scoped preload. The pin never moves with a Puppeteer bump alone: a new Firefox passes the full Firefox smoke and network lanes first.

## What Firefox does differently, and where it is absorbed

| Firefox behaviour | Symptom if ignored | Where it is handled |
|---|---|---|
| MV3 background is an event **page**, not a service worker: no `service_worker` target, nothing to kill over the protocol, and **no successor until the add-on's next event** (Chrome restarts its worker within milliseconds). It can be ended alone only from Firefox's privileged scope, and only politely: **with an extension page open Firefox leaves it running and still reports the call done**. | A wait for the worker target burns its whole timeout; a kill under an open popup kills nothing. | `stopBackground` / `backgroundAlive` on the driver. Chrome: an unattached `Target.closeTarget`. Firefox: the privileged termination through `chromeScript`, resolved once the old page's `performance.timeOrigin` is gone and rejecting by name if the page outlives the call. **Close every extension page before the kill** (a dApp page's content script does not hold the background); the spec's next step — opening the popup, a dApp click — is what wakes the successor, then gate on `waitForWorkerLiveness`. A dApp with a call pending is such an event too (the SDK heartbeats only while a call is in flight): in the two kills of `inflight-call-background-death` that open nothing, with every alarm cleared, the successor is up within the budget — suggestive, one end-of-budget sample per kill — which is also why a dApp's in-flight call is rejected within seconds on Firefox (the successor answers the forgotten session with `session-disconnected`, `wallet-sdk/stale-session.ts`) rather than at the dApp's 300 s ceiling. `storage.session` survives the kill on both browsers, so the lock that follows is strict mode's. | A new **tab** goes into the most recently focused window — which can be one the wallet opened, such as an approval window. | The page may never be visible: no animation frames, every Vue `<Transition>` freezes half-way (`sheet-enter-from sheet-leave-active`), and `browsingContext.create` can fail with `browsingContext is null`. | `newPage` opens a **window** (`{ type: "window" }`). | No `chrome.offscreen`: the PXE host is a **frame of the background page**, and dies with it. | Headless Firefox gives **focus** to every window the wallet opens (ignoring `focused: false`), and raises it once more as it starts loading that window's page. | A click on a file input opens **Firefox's native picker** only while the page holds user activation. ## CSP violations

The recorder (README § CSP violations) hears the same contexts on both browsers. On Firefox the background is a page, so it listens on its window rather than a worker's global, and the offscreen document is one of its frames, which forwards its violations to the page over `runtime.sendMessage` like every other document.

## The egress guard's routing

Every guarded launch, smoke or network (README § Egress guard), adds five prefs, `egressGuardPrefs` in `firefox.ts`, and never puts them in `FIREFOX_LAUNCH_PREFS`, which holds what users run with: `network.proxy.type: 2` with a `data:` PAC in `network.proxy.autoconfig_url` that answers `DIRECT` for `localhost`, `127.0.0.1`, `::1` and `[::1]` and `PROXY 127.0.0.1:<guard>` for every other host, with nothing after it; `network.proxy.failover_direct: false`, so a dead guard fails a request instead of sending it out; and `network.dns.localDomains: "egress-canary.test"`, so the canary name resolves to loopback for a direct path only; and `browser.newtabpage.trainhopAddon.xpiBaseURL: ""`, New Tab's off state for the add-on update a Nimbus enrollment names, which Firefox 158 otherwise fetches from `archive.mozilla.org` on a fresh profile. They are all prefs, rather than the W3C `proxy` capability, because the fail-over and DNS prefs have no capability form. Firefox retries its own refused requests about ten times a second, all under Mozilla's remote-settings hosts (`FIREFOX_OWN_HOSTS`), which is why the guard keeps a count per host rather than an entry per attempt. Each host the launch sends direct gets one PAC line before the proxy, `DIRECT` for that name compared with `===`, so those names alone resolve and connect as usual: bb.js's CRS hosts (`CRS_HOSTS`) on every guarded launch, and the Testnet node's and the token list's hosts on the live spec's launch.

## Artifact mode (the release and nightly smokes)

`NULO_E2E_ARTIFACT_RUN=1` smokes a production bundle behind the same guard and prefs as a source build, so the price host and every other outside host but the CRS hosts are refused at the guard and the stand-in answers the node. Only the live spec's launch differs, by its two `DIRECT` lines above and no stand-in.

## Ownership and teardown

A Firefox launch owns more than a browser process: geckodriver, the Firefox it spawned, and a profile directory. `ownership.ts` finds them by an environment marker (`NULO_E2E_LAUNCH=<uuid>`, with `NULO_E2E_OWNER=<pid>:<start time>` of the test worker, inherited by both processes, read back from `/proc/<pid>/environ` through `owned-processes.ts`), never by name — many agents run on one host and a `pkill geckodriver` would take down someone else's run. The record is on disk before geckodriver is spawned, then names its pid and start time. The marker is re-checked immediately before every signal, a sweep of an orphaned record signals a process only once the owner in its own environment is dead, and a recorded geckodriver still running but unreadable keeps the profile and record on every sweep. A profile is deleted only if it sits directly under the suite's profile root, carries the `profile-` prefix and holds a `.nulo-launch` file matching the marker. Each launch first reaps the launches of runs that no longer exist, and `bun run e2e:reap` does the same on demand — run it after the last Firefox run of a session, since nothing else will until the next launch. Always end a launch through `ctx.close()`; closing the `Browser` leaks all three.

## Debugging a Firefox-only failure

1. Reproduce one file at retry 0: `NULO_E2E_BROWSER=firefox NULO_E2E_RETRY=0 bun run e2e:agent <file>`.
2. Check the page is **visible and focused** first — `document.visibilityState`, `document.hasFocus()`. Most early failures were a page in the wrong window, not the thing the assertion named.
3. A stuck transition, a missing rAF or a 1 Hz timer means a hidden document. A `NotAllowedError` at 0 ms means focus, and so does a key whose events fire but whose action does not. A timeout on a picker or a permission prompt means user activation.
4. An error matching `no such frame | Browsing Context … not found | DiscardedBrowsingContext | Browsing context already closed` is a closed window (`targetGone`); on an approval click that is the expected end. The last wording is Puppeteer's own, for a realm disposed before the command fails.
5. Measure in the page before changing a fixture. Three of this suite's wrong turns were fixes for symptoms; the cause each time was a page opened in the wrong window (above). A fourth masked the PXE's timer throttling with launch prefs instead of moving the host.

## Picturing the toolbar panel

The toolbar panel has no Puppeteer target, so `page.screenshot` cannot take it. Draw it from the privileged scope instead (`session.chromeScript`):

1. Find the open panel's browser: the `.webextension-popup-browser` that is not `.webextension-preload-browser`, under a `panel` whose `state` is `open`.
2. Call `browsingContext.currentWindowGlobal.drawSnapshot(null, 2, "white")` on it.
3. Draw the bitmap on a canvas made from the browser's `ownerDocument`. `ownerGlobal` reads `undefined` in that scope, and a throw inside the promise's callback leaves the script hanging until its timeout.

A hand-off window opened by hand must name the last-focused normal window as its opener, as the panel does. The background reopens the panel only where focus returns.

## CI

`pr-extension-{smoke,network}-e2e-firefox.yml` are twins of the Chrome callers with `browser: firefox`; `nightly.yml` and `release.yml` carry Firefox jobs too. The two PR aggregators are required on `dev` and `main`; the nightly Firefox jobs gate the nightly's publish. Outside the PR lanes' own aggregators, a Firefox job is in the `needs` of two workflows' gates: `nightly.yml`'s `publish-nightly` and `status` wait on every nightly Firefox job, and `release.yml`'s `attach-assets` and `status` wait on its smoke of the shipped zip. The lanes are not free: the PR lanes start nineteen more jobs (thirteen suites, six control) on a PR that trips both filters, drafts included, and queue against the required lanes for the same runners, and `release.yml`'s Firefox smoke holds the `release` concurrency slot until it ends (a 45-minute execution timeout; time queued for a runner is on top). `scripts/ci-cd/behavior-gating.test.ts` pins that wiring and the parity with the Chrome lanes. geckodriver is pinned by tarball and binary SHA-256 in `.github/actions/setup-geckodriver`; Firefox itself is the suite's pin, not Puppeteer's (§ [Which Firefox the suite runs](#which-firefox-the-suite-runs)). A change to a branch's required set is the owner's call (root `CLAUDE.md`; the release skill's staged-rollout switches).

## The add-on linter's parse limit

`web-ext lint` (the AMO validator) refuses to parse a file of 5 MiB or more and reports it as an error. The build keeps every parsed file under 4.5 MiB and fails, naming the file, when one is not — the mechanisms and what to do when the guard fires are in [`apps/extension/README.md`](../../README.md) § Key invariants. Check a build with `bunx web-ext@10.6.0 lint --source-dir apps/extension/dist/firefox --self-hosted`: zero errors is the bar; warnings are reviewed, not counted.
