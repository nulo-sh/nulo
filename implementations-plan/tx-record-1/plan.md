# tx-record-1: what a dApp transaction's record stores, and what History and the transaction page say

Two arcs, each one PR against `dev`, not stacked (the orchestrator's D-orch-1). **A1** writes a dApp send's class before its estimate (#820); no open ask touches it. **A2** classifies the window's end of a queued send (#828, OA-2 = B: the window names its end and the wallet takes it before the window closes) and records who chose a transaction's fee (#821, OA-1 = B), with the close-out. ## Outcome & Quality Bar

- **For whom:** a person reading History, or one transaction's page, after a dApp asked them to send.
- **Excellent:** (1) a send whose estimate fails at the send reads the movement name its settled row would, on a token the person listed; (2) a send the person rejected, with the button or the window's X, reads "Cancelled" and "You rejected" under the name it had while it waited, the same on every run, and the button answers the app 4001; a lock reads "Stopped when the wallet locked"; a profile switch keeps "Popup closed early"; (3) the Fee method row names a method for the app's pick only when a contract address proves it, and never calls an app's own sponsor "Sponsored"; (4) a row saved before this change reads exactly as today.

## Architecture & Implementation

### A1 · #820: every build of the send names its record before its simulation

- **Hook.** `FeeStrategyContext.onBuilt?: (txCalls: BuiltStandardTx["txCalls"]) => Promise<void>` (`wallet/services/execution/fee/fee-strategy.ts`), documented as "absent on every estimate". One helper beside it, `buildFor(txBuilder, ctx, method, task)`, runs `buildStandard(ctx.op, ctx.fence, method, task, appPriorityOf(ctx.op.fee))` (the argument list all nine sites repeat today) and then awaits `ctx.onBuilt?.(built.txCalls)`. Every site calls it: `fee/fee-juice-strategy.ts:36,54`, `fee/fee-juice-with-claim-strategy.ts:29`, `fee/embedded-strategy.ts:42`, `fee/fpc-strategy.ts:153,185,229,263,283`. Every build, not only the first: a rebuild can resolve a class the first build's `node.getContract` missed (`tx-request-builder.ts:576-581`), and its simulation can still fail. The classic discovery build fires it too: `DiscoveryAwareEstimatorDeps.buildForDiscovery(op, method, fence, onBuilt?)` (`wallet/services/execution/service.ts:479-489`).
- **Threading, per call.** One trailing optional argument, never on a constructor's deps (the estimator and the strategies are shared with the window): `ExecutionService.buildAndEstimateTxRequest(..., fpc?, onBuilt?)` → ctx; `DappSendExecutorDeps.buildAndEstimateValidated(..., signal?, onBuilt?)`; `DiscoveryAwareEstimatorDeps.buildAndEstimateValidated` / `buildAndEstimateFolded`; `DiscoveryAwareEstimator.estimate(..., signal?, onBuilt?)`. The executor passes the slot's `recordCall` from `sendTransactionPass` (`dapp-send-executor.ts:848`) and from `resolveStandardBuild` (its embedded arm `:1164` and the estimator `:1172`, through a new parameter from `standardPass`). `buildForEstimate` (`:589,592`) passes nothing. The hook is the record's one writer (as built: the two post-build `recordCall`s repeated the last hook's write, so they are gone, and a reused estimate, which runs no build, hands its retained calls to the hook in `resolveStandardBuild`'s reuse arm). `recordBuiltCall` is best-effort and never throws (`execution-lane.ts:671-685`), so the hook cannot fail a send; a failed send keeps the record's `call` (`operation-journal/service.ts:388-391`).

### A2 · #828: the window names its end, and the wallet takes it before the window closes

- **The field.** `rejectInteraction(id, reason, end)` (`wallet/services/dapp-interaction/spec.ts`) gains `end: WindowEnd`, one of `"reject" | "close" | "lock" | "switch"` (new `dapp-interaction/window-end.ts`, beside `WindowEndedError extends UserRejectedError`, which carries it). The service validates it (`isWindowEnd`; the RPC boundary is untyped) and cancels the handle with `new WindowEndedError(reason, end)`; an absent or unknown end cancels with a plain `UserRejectedError`, today's reading. The subclass keeps the envelope's 4001 `USER_REJECTED` (`error-envelope.ts:75`), and `interaction()`'s refusal arm still replaces it (`instanceof UserRejectedError`).
- **The window names it.** `useDappApprovalWindow`'s `reject` option takes the end: `beforeunload` → `"close"`; the profile watch → `"lock"` when no profile is active, `"switch"` for another one; each window's Reject button → `"reject"`. All four windows (execute, capabilities, discover, fee) pass it through `useDappInteractionPayload.reject(reason, end)`, which returns the RPC's promise.
- **The wait.** One composable helper, `endAndClose(send)`: it removes the `beforeunload` listener first (no second end on the close), sends, and closes the window when the wallet answers, when the send fails, or after `END_ACK_TIMEOUT_MS` (3 s), so a wedged worker cannot hold the window open. The send posts synchronously on a connected port (`packages/extension-messaging/src/core/base-client.ts:119-135`), so the X's end still leaves during `beforeunload`. Taking the end settles the dApp's request and removes the window (`window-manager.ts:160,247`), so the button's 4001 no longer races the close's generic error.
- **The classifier.** `queuedFailureKind` (`wallet-sdk/queued-journal.ts`), after the refusal arms: a `WindowEndedError` maps `reject` and `close` to `user_rejected`, `lock` to `session_ended`, `switch` to `popup_bound`; `WINDOW_CLOSED_BY_USER` (the close reached the wallet first: an X whose end was lost, or a window that closed without naming one) maps to `user_rejected`. `QueuedFailureKind` gains `"user_rejected"`. `failQueuedIfUnclaimed` keeps the title for `popup_bound` and `user_rejected` through one named set; `session_ended` retitles to "Transaction" as every lock does today, the reading OA-2's B picture showed.
- **Stored.** No new persisted field: the three kinds exist in the journal's schema, and the journal is not in a full backup (`utils/full-backup-helpers.ts` carries accounts, transactions, authwits, token balances and config).
- **Limits.** A lock or switch whose end never reaches the wallet falls to the close and reads "You rejected" if the person then closes the window: the worker dies between the event and the send, or the lock lands before the window has loaded its request (every window reads the active profile first, and its Reject is inert until the request id is loaded, a pinned guard; the window then routes to the lock screen and stays open). The window's timeout keeps "Popup closed early". The X answers the app 4001 or the generic error, whichever reaches the wallet first, as today; making the close answer 4001 is the separate decision OA-2 named. "Every time" is the race: a request the wallet already refused still answers its refusal on Reject (4100, `dapp-interaction/service.ts:637`), as before.

### A2 · #821: who chose the fee, on the transaction record

- **Field.** `wallet/services/transaction/spec.ts`: `FEE_CHOICES = ["wallet", "app", "app_protocol_sponsor"] as const`, `Tx.feeChoice?: FeeChoice`, `TxSchema.feeChoice: z.enum(FEE_CHOICES).optional().catch(undefined)` (an unknown value reads as absent and the row still reads, as `priorityLevel`). `AddTransactionInput.feeChoice?` and the conditional spread in `transaction/service.ts:181-244`. Restore accepts it through the same schema; no migration (pre-production, CLAUDE.md § Persisted-storage shape changes).
- **Write-time match.** `feeChoiceOf(by, calls, protocolSponsor)` in a new `wallet/services/execution/fee-choice.ts` (pure): `"wallet"` for the wallet's pick; for the app's, `"app_protocol_sponsor"` when any call is `sponsor_unconditionally` with `sameFieldAddress(contract, protocolSponsor)`, else `"app"`. Any position: the app orders its calls, and a decoy fee call ahead would withhold a proven label; that call running proves the payer (F8). The address comes from one new dep, `DappSendExecutorDeps.protocolSponsorAddress(chainId): Promise<string | undefined>`, wired in `execution/service.ts` to `fpcService.getOrComputeProtocolAddresses(chainId)` (`fpc/service.ts:103-115`, where the wallet already derives it); a failed derivation gives `undefined`, so the row reads "Set by {app}", which is never wrong.
- **Writers.** `SentTx` gains `feeChosenBy: "wallet" | "app"`, from `op.feeSettings.paymentMethod.kind === "embedded"` in `proveStandardSend` and `proveSendTransaction` (the materializer sets `embedded` exactly when the request embeds its fee, `dapp-interaction/materialize.ts:59`); `sentTxRecorder` derives only for the app's pick. The no-from writer (`dapp-send-executor.ts:1253`, fee always embedded) writes the app's. `recordTransfer` (`transfer-executor.ts:439-480`) writes `"wallet"`.
- **Label.** `describeFeePaymentMethod` (`tx-detail-helpers.ts`): `FeePaymentLabelInput` gains `feeChoice?: string`. An unknown `feePaymentMethod` reads "Unknown (n)" whoever chose. An app pick reads `Public Fee Juice (with claim), set by {app}` for `FEE_JUICE_WITH_CLAIM` (the wallet's own entrypoint makes that claim, `fee/embedded-strategy.ts:34-37`); for `EXTERNAL`, `Sponsored, set by {app}` for `app_protocol_sponsor`, `Private Fee Juice, set by {app}` when any call is `pay_fee` or `mint_and_pay_fee` on the PrivateFPC (`isPrivateFpc`, the pin the page reads), else `Set by {app}`; `{app}` is `origin.name ?? "the app"`. A wallet pick keeps today's first-fee-call rule (its own fee call is first, `fee/fpc-strategy.ts:152,201`) and labels, except that its `EXTERNAL` fallback is "External FPC", never "Set by {app}". A row with no `feeChoice` reads exactly today's labels. `popup/pages/tx/[id].vue:280` gains `data-testid="tx-detail-fee-method"` (no visual change).

### Trade-offs and alternatives not taken

- **#820, the first build only**: misses a class a rebuild recovers (Codex r1). **A class read in the executor before the build**: a second source of the class plus a network read on every send. **The hook inside `buildStandard`** (outline B): `view-executor.ts` and the discovery build call it too, and the per-call threading is the same; the strategy helper keeps it where the fee code already shares its build arguments.
- **#828 at `interaction()`'s catch** (outline B): turning the close into `UserRejectedError` there changes what every window type answers a dApp (capabilities, discover), an unsigned contract change. **OA-2's A** (classify every end alike): no handshake, but a lock and a switch read "You rejected"; the owner chose B. **The end on the window manager's handle** instead of the error: a second channel for the same fact, and the ingress already classifies by the error's class. **An unbounded wait**: a wedged worker would leave Reject doing nothing.
- **#821, two fields**: allows a wallet pick flagged as the app's sponsor. **The kernel's fee payer as proof**: sound, but each path holds it in a different object and a reused estimate carries no `appPayer` (`dapp-send-executor.ts:1141-1157`); the calls are in every writer's hand. **Who chose, declared by each strategy** (outline B): no strategy runs on a reuse or on no-from.

## Security & Adversarial Considerations

- **Threat model.** A hostile dApp names its functions, orders its calls and picks its fee contract; a hostile backup row sets `feeChoice`, `origin` and `calls`. The worst result is a wrong label on the person's own record, which feeds no send, fee, authorization or key. A dApp can no longer get "Sponsored" for its own contract; it gets "Sponsored, set by {app}" only by calling the protocol sponsor, which then pays (F8), and no call order withholds it. A dApp cannot produce `user_rejected` or name an end: `rejectInteraction` is an extension-internal service method no dApp message reaches, and a page cannot close the window. An extension page that names a false end only mislabels a request it could already reject; an unknown end reads as today. A backup the person imports can still claim any of the three labels, as it can today through `origin` and `calls`: authenticating imported history would add a provenance contract and a key lifecycle for a label (both legs: keep it a limit; the restore tests pin that an unknown value reads absent).
- **Input validation.** `feeChoice` passes one closed enum at the schema every read and restore uses. `{app}` is the session's sanitized name, rendered as text, as "Set by {app}" already is. The early journal write takes the build's calls through `journalCallOf`'s bounds (`safeParse`), as the post-build write does.
- **Boundaries.** The window's estimates never write the journal: the hook is a per-call argument the estimate path does not pass, on a context built fresh per call (`service.ts:1355-1365`); unit and composition tests pin it. No new permission, message, storage root or background work; the derivation is the cached one the FPC service already runs.
- **Logging.** No new log line carries a record; a failed derivation logs a fixed category at `debug` (logging-policy skill).
- **Supply chain / crypto.** No new dependency; no cryptography.
