## Architecture & Implementation

### A1 · #820: every build of the send names its record before its simulation

- **Hook.** `FeeStrategyContext.onBuilt?: (txCalls: BuiltStandardTx["txCalls"]) => Promise<void>` (`wallet/services/execution/fee/fee-strategy.ts`), documented as "absent on every estimate". One helper beside it, `buildFor(txBuilder, ctx, method, task)`, runs `buildStandard(ctx.op, ctx.fence, method, task, appPriorityOf(ctx.op.fee))` (the argument list all nine sites repeat today) and then awaits `ctx.onBuilt?.(built.txCalls)`. Every site calls it: `fee/fee-juice-strategy.ts:36,54`, `fee/fee-juice-with-claim-strategy.ts:29`, `fee/embedded-strategy.ts:42`, `fee/fpc-strategy.ts:153,185,229,263,283`. Every build, not only the first: a rebuild can resolve a class the first build's `node.getContract` missed (`tx-request-builder.ts:576-581`), and its simulation can still fail. The classic discovery build fires it too: `DiscoveryAwareEstimatorDeps.buildForDiscovery(op, method, fence, onBuilt?)` (`wallet/services/execution/service.ts:479-489`).
- **Threading, per call.** One trailing optional argument, never on a constructor's deps (the estimator and the strategies are shared with the window): `ExecutionService.buildAndEstimateTxRequest(..., fpc?, onBuilt?)` → ctx; `DappSendExecutorDeps.buildAndEstimateValidated(..., signal?, onBuilt?)`; `DiscoveryAwareEstimatorDeps.buildAndEstimateValidated` / `buildAndEstimateFolded`; `DiscoveryAwareEstimator.estimate(..., signal?, onBuilt?)`. The executor passes the slot's `recordCall` from `sendTransactionPass` (`dapp-send-executor.ts:848`) and from `resolveStandardBuild` (its embedded arm `:1164` and the estimator `:1172`, through a new parameter from `standardPass`). `buildForEstimate` (`:589,592`) passes nothing. The post-build `recordCall` stays: it is the only write on an estimate reuse and the final word on success. `recordBuiltCall` is best-effort and never throws (`execution-lane.ts:671-685`), so the hook cannot fail a send; a failed send keeps the record's `call` (`operation-journal/service.ts:388-391`).

### A2 · #828: the window's end fails the queued record as `user_rejected`

`wallet/services/wallet-sdk/queued-journal.ts`: `QueuedFailureKind` gains `"user_rejected"`; `queuedFailureKind` returns it for `error instanceof UserRejectedError || error === WINDOW_CLOSED_BY_USER`, after the refusal arms (a recorded refusal already replaces the Reject upstream, `dapp-interaction/service.ts:634-639`). `failQueuedIfUnclaimed` keeps the title for the two kinds the window ended, `popup_bound` and `user_rejected`, through one named set; every refusal kind still retitles. Its docstring and `packages/wallet-core/src/jobs/types.ts:135-136` ("not all produced on HEAD") are corrected. The labels already exist (`utils/journal-state.ts`). This is OA-2's A; a B or C answer replaces this paragraph before A2 starts.

### A2 · #821: who chose the fee, on the transaction record

- **Field.** `wallet/services/transaction/spec.ts`: `FEE_CHOICES = ["wallet", "app", "app_protocol_sponsor"] as const`, `Tx.feeChoice?: FeeChoice`, `TxSchema.feeChoice: z.enum(FEE_CHOICES).optional().catch(undefined)` (an unknown value reads as absent and the row still reads, as `priorityLevel`). `AddTransactionInput.feeChoice?` and the conditional spread in `transaction/service.ts:181-244`. Restore accepts it through the same schema; no migration (pre-production, CLAUDE.md § Persisted-storage shape changes).
- **Write-time match.** `feeChoiceOf(by, calls, protocolSponsor)` in a new `wallet/services/execution/fee-choice.ts` (pure): `"wallet"` for the wallet's pick; for the app's, `"app_protocol_sponsor"` when any call is `sponsor_unconditionally` with `sameFieldAddress(contract, protocolSponsor)`, else `"app"`. Any position: the app orders its calls, and a decoy fee call ahead would withhold a proven label; that call running proves the payer (F8). The address comes from one new dep, `DappSendExecutorDeps.protocolSponsorAddress(chainId): Promise<string | undefined>`, wired in `execution/service.ts` to `fpcService.getOrComputeProtocolAddresses(chainId)` (`fpc/service.ts:103-115`, where the wallet already derives it); a failed derivation gives `undefined`, so the row reads "Set by {app}", which is never wrong.
- **Writers.** `SentTx` gains `feeChosenBy: "wallet" | "app"`, from `op.feeSettings.paymentMethod.kind === "embedded"` in `proveStandardSend` and `proveSendTransaction` (the materializer sets `embedded` exactly when the request embeds its fee, `dapp-interaction/materialize.ts:59`); `sentTxRecorder` derives only for the app's pick. The no-from writer (`dapp-send-executor.ts:1253`, fee always embedded) writes the app's. `recordTransfer` (`transfer-executor.ts:439-480`) writes `"wallet"`.
- **Label.** `describeFeePaymentMethod` (`tx-detail-helpers.ts`): `FeePaymentLabelInput` gains `feeChoice?: string`. An unknown `feePaymentMethod` reads "Unknown (n)" whoever chose. An app pick reads `Sponsored, set by {app}` for `app_protocol_sponsor`, `Private Fee Juice, set by {app}` when any call is `pay_fee` on the PrivateFPC (`isPrivateFpc`, the pin the page reads), else `Set by {app}`; `{app}` is `origin.name ?? "the app"`. A wallet pick keeps today's first-fee-call rule (its own fee call is first, `fee/fpc-strategy.ts:152,201`) and labels, except that its `EXTERNAL` fallback is "External FPC", never "Set by {app}". A row with no `feeChoice` reads exactly today's labels. `popup/pages/tx/[id].vue:280` gains `data-testid="tx-detail-fee-method"` (no visual change).

### Trade-offs and alternatives not taken

- **#820, the first build only**: misses a class a rebuild recovers (Codex r1). **A class read in the executor before the build**: a second source of the class plus a network read on every send. **The hook inside `buildStandard`** (outline B): `view-executor.ts` and the discovery build call it too, and the per-call threading is the same; the strategy helper keeps it where the fee code already shares its build arguments.
- **#828 at `interaction()`'s catch** (outline B): turning the close into `UserRejectedError` there changes what every window type answers a dApp (capabilities, discover), an unsigned contract change. **Telling the window's ends apart** (OA-2's B and C): the window would pass its end with the Reject it sends, a new field on an internal call, and the wallet must hold it before the window closes, or the close wins the race; tests would force both settlement orders. Taking the Reject settles the dApp's request (`dapp-interaction/service.ts:326,330`), so the button's answer would become 4001 every time instead of racing the generic error; OA-2 states that consequence.
- **#821, two fields**: allows a wallet pick flagged as the app's sponsor. **The kernel's fee payer as proof**: sound, but each path holds it in a different object and a reused estimate carries no `appPayer` (`dapp-send-executor.ts:1141-1157`); the calls are in every writer's hand. **Who chose, declared by each strategy** (outline B): no strategy runs on a reuse or on no-from.

## Security & Adversarial Considerations

- **Threat model.** A hostile dApp names its functions, orders its calls and picks its fee contract; a hostile backup row sets `feeChoice`, `origin` and `calls`. The worst result is a wrong label on the person's own record, which feeds no send, fee, authorization or key. A dApp can no longer get "Sponsored" for its own contract; it gets "Sponsored, set by {app}" only by calling the protocol sponsor, which then pays (F8), and no call order withholds it. A dApp cannot produce `user_rejected`: only the window reaches `rejectInteraction`, and a page cannot close the window. A backup the person imports can still claim any of the three labels, as it can today through `origin` and `calls`: authenticating imported history would add a provenance contract and a key lifecycle for a label (both legs: keep it a limit; the restore tests pin that an unknown value reads absent).
- **Input validation.** `feeChoice` passes one closed enum at the schema every read and restore uses. `{app}` is the session's sanitized name, rendered as text, as "Set by {app}" already is. The early journal write takes the build's calls through `journalCallOf`'s bounds (`safeParse`), as the post-build write does.
- **Boundaries.** The window's estimates never write the journal: the hook is a per-call argument the estimate path does not pass, on a context built fresh per call (`service.ts:1355-1365`); unit and composition tests pin it. No new permission, message, storage root or background work; the derivation is the cached one the FPC service already runs.
- **Logging.** No new log line carries a record; a failed derivation logs a fixed category at `debug` (logging-policy skill).
- **Supply chain / crypto.** No new dependency; no cryptography.

## Assumptions

**Facts:** F1 `user_rejected` is a known kind with labels already pinned (recon reuse map). F2 the Reject's `UserRejectedError` reaches the ingress as the same instance (recon § #828). F3 the class is set inside `buildStandard` before any strategy simulation (`tx-request-builder.ts:576-584`). F4 a failed send keeps the record's `call` (`operation-journal/service.ts:388-391`). F5 `TxSchema` strips an unknown key on read and restore (`transaction/service.ts:118,627`). F6 only two FPC row types exist; on the FPC injection paths the wallet's fee call is first (`fee/fpc-strategy.ts:152,201`). F7 the derivation helpers take no chain input; `getOrComputeProtocolAddresses(chainId)` caches per chain. F8 at 6.0.0-rc.3 the private kernel refuses a second fee payer ("Cannot overwrite non-empty fee_payer", `@aztec-labs/noir-protocol-circuits-types` `artifacts/private_kernel_inner.json`), the SponsoredFPC's `sponsor_unconditionally` elects itself unconditionally (`@aztec-labs/noir-contracts.js` `artifacts/sponsored_fpc_contract-SponsoredFPC.json`), and the row is written only after the send (`execution-coordinator.ts:336-353`): a recorded transaction that calls it was paid by it. **Inferences:** I2 an app's call to the canonical SponsoredFPC is recorded with the name its selector resolves to (`tx-request-builder.ts:207-216`; no-from `:357-363`). I3 `WINDOW_CLOSED_BY_USER` means the window went away while its request was open, never an approve (the wallet detaches first, `dapp-interaction/service.ts:265`); it does not say why.
