## Outcome & Quality Bar

**For whom.** A person using the popup (Chrome or Firefox, light or dark), a person onboarding in a tab, a Firefox user whose loopback permission is missing, and the owner preparing store art.

**What excellent looks like.**
1. History opened from a token page holds exactly the rows the token page counts as that token's (the same predicates, shared), never a row of another token, and never paints a list or an empty state before it knows the token. The chip names the token; clearing it, or the History tab, shows everything.
2. Onboarding never paints a theme the person did not choose, never writes the paint hint before it has read the stored choice, and survives a background restart during the read; a read that fails keeps the pre-paint theme.
3. Old Account State URLs land on the same pages under Developer; nothing a person sees changes but the URL. A second toolbar click on a running Full Backup flow on Firefox brings the open window forward with the window manager's call (`focused`, `drawAttention`, `state: "normal"`), and never opens a second one, or focuses a window that is not the flow's.
4. On Firefox, a missing loopback permission is named in the approved words, Allow asks the browser at the click, the control is reachable by keyboard with the accent ring, and once the permission is present (granted here or in about:addons) the page checks Presto at once. Chrome never shows the row.
5. The store Send frame shows the amount line whole, verified after the scroll; the owner sees the before and the re-staged capture side by side. Nothing is uploaded, and no committed store art changes.

**Good enough.** No chip update across windows; no announcer for the clear action; no Chrome permission step; onboarding does not repaint on a theme change made elsewhere while it is open (OA-8). The own-window guard is per browser session; a repeated start from the same panel shares one open, and the one residual is a start from a re-opened panel during the new window's boot, before it registers (D7).

### Arc 2

**#156, the Firefox loopback permission (P13-04).**
- Phase 2.1 probes I1-I3 on Firefox before any build (D9, D10).
- `composables/usePrestoHostPermission.ts` (new, C1): `{ access: Readonly<Ref<"unknown" | "missing" | "granted">>, request(): Promise<boolean>, dispose(): void }`.
  - Origins: the manifest's own entries from `chrome.runtime.getManifest().host_permissions` whose scheme is `http` or `https` and whose host equals `PRESTO_HOST` (`presto/config.ts`) exactly. An empty set means nothing to ask: `access` is `granted` and an error is logged once (the manifest pin fails first in CI).
  - Not Firefox (`isFirefox()`): `access` is `granted` from the start; no permission API is called. Chrome's behaviour is unchanged.
  - Firefox: `access` starts `unknown`, then follows `chrome.permissions.contains({ origins })`, read at setup and on `chrome.permissions.onAdded` / `onRemoved`. Reads are fenced, so an older answer never lands over a newer one, and nothing lands after `dispose()`, which removes both listeners. A read that throws leaves `granted` (the step is an aid; the probe reports what it finds) and logs a fixed category at `debug`.
  - `request()` calls `chrome.permissions.request({ origins })` with no `await` before it (the click's user input must hold), returns the browser's boolean, and re-reads `access`. A refusal or a throw returns false and logs a fixed category at `debug`, never the browser's error text.
- `composables/usePrestoCheck.ts` gains an optional `access` ref, so the probe policy stays in its one owner ("no probe the browser does not allow"). ## Security & Adversarial Considerations

- **A crafted History URL.** `?token=` must be one string of digits naming a safe integer above 0, looked up among the active scope's tokens; anything else is no filter. It cannot widen scope: `buildActivityRows`' account, profile and network rules run first, and the filter only removes rows. An id from another scope never resolves, and the page drops the query.
- **A hostile token symbol** (`token/spec.ts` warns the strings are not authentic). The chip shows `sanitizeWireString(symbol, 32)`, as the token page does for reused symbols (F18), so bidi overrides and zero-width characters cannot reorder the "×" or overflow the hero; Vue text interpolation, never `v-html`; the accessible name is fixed text, so the symbol never enters an attribute.
- **Theme.** The config read crosses the port to the background; the config schema admits only `dark | light | system`, and `theme-boot.js` clamps the hint.
- **Redirects.** Exact-path records with fixed targets; a forwarded query rides along but cannot change the target, and the target's own `isAuthRequired` decides (pinned by the file's test). No open redirect.
- **Own windows.** The stored window id is written only by the extension's own documents to `chrome.storage.session`, which content scripts cannot read by default. A document registers only when its window is `popup`-type, and the panel focuses only a `popup`-type window, so a marked URL restored in a tab can never make the panel focus the person's browser window and close. A document that lands outside its flow, other than on its way back through the unlock page, releases its registration, so a stale id names a closed window (a new window opens) or a window showing or returning to its flow. No new permission: `windows.get` and `windows.update` need none, and no `tabs` permission is added.
- **The permission request.** It names only the manifest's own loopback entries with an exact host match, read from `getManifest()`, so a code change cannot request a broader origin without the manifest pin failing. No optional permission is added unless Firefox requires it, and never on Chrome. The request runs only inside a click. Logs carry a fixed category, never the browser's error text.
- **Presto trust.** Granting the permission changes reachability only; Presto's per-origin approval and the HTTPS-only proving transport (`presto/client.ts:17`) are unchanged.
- **Store art.** The arc uploads nothing and leaves `apps/extension/store/` unchanged in git; the comparison shots live in the plan directory.
- **Supply chain.** No new dependency. Crypto: none.
