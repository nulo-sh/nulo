# Owner asks: harden-security-fixes-4

Neither arc changes what a person sees. One question outside both arcs went to the owner; nothing waited on it.

## OA-1: what a full-backup export does when its contract part is larger than an import accepts

- **Surface:** Settings → Security → Export → Full backup, at the moment the file is made, and what a later restore brings back.
- **Today, measured on the local network:** the export always finishes with "Backup downloaded successfully". The part of the file that carries the registered contracts and their code (the `account-state` part, one for all networks) grows by about 1.8 million characters for each registered contract, because each carries its own copy of its contract's code. Every token held is one; a contract an app registers counts the same way. Past about 23 of them across the profile's networks that part is larger than an import accepts (41,943,040 characters), and a later restore lists it as refused on its errors screen: the tokens restore through their own part of the file; the saved senders and the other contracts in the refused part do not. Past about 27 the file passes 64 MiB and the export refuses with "Backup is too large to create".
- **What ships now, with no visible change:** nothing new. A test already holds the export's size warning and the import's refusal to one bound (`apps/extension/src/wallet/services/account-state/service.test.ts`, "against the import's slice cap").
- **Option A, keep today's behaviour:** the export says nothing; the restore reports the refused part.
- **Option B, refuse at export:** no file is made, with the toast the export already shows past 64 MiB, "Backup is too large to create". No new words; the person has no full backup until they remove tokens.
- **Option C, leave the contracts out and say so:** the file is made without the registered contracts' code; the senders stay, being small. The result screen shows a warning banner above "Saved to your downloads", in the pattern of the banner a profile in recovery mode already gets ("Local chain data is not in this backup"), keeping that banner's consequence line. Draft words: title "Some chain data is not in this backup"; text "Its contract data is larger than a restore accepts, so the registered custom contracts were left out. After the restore, register them again. Until then their private notes stay undiscovered, since a network sync cannot rebuild that material." The restore then refuses nothing.
- **Option D, later and its own plan, no visible change: leave out code the wallet ships.** The export already leaves out the contracts every wallet start registers by itself. It could also leave out a token's contract whose code ships with the wallet (the standard token contract): a restored token registers its contract again from the network and the wallet's own copy of the code, and the part keeps its shape. Tokens would stop counting toward the limit. As first drafted it does not hold: a contract of a shipped kind that an app registered with no token beside it (an NFT, a fee contract) would lose its registration, and a restore on a wallet build that ships different code finds no copy to fall back on. It needs a rule naming exactly which entries may go (only those a restored token row brings back) and an answer for restores across builds, so it is a plan of its own.
- **Recommendation:** C now, and D after it as its own plan. B leaves a person with no backup at all; A tells them only at restore, when it is too late to act. C reuses a banner the screen already has and keeps its warning about undiscovered notes; its words are a draft for the owner's edit. D would then keep most token holders below the limit with nothing on screen.
- **Frames:** light and dark, at the popup's size, for today, B and C (listed in the orchestrator's report). D shows nothing.
- **Answer (2026-11-23, with the frames):** none of the options. The owner: "It doesn't feel like any of this options provides a good UX solution for them? Would for example saving the contract's address but fetching their artifacts from say... Aztecscan make sense? Or... I am not sure. Seems like this are lazy solutions." The design continues as a plan of its own, on what a full backup keeps of a registered contract, now being written.
