# Phase 4: Firefox e2e, docs, captures

- The new scenario passed at retry 0 (16.3 s and 17.7 s in two runs, against an estimate of 25 s). It went red with the hand-back off: a mutation making `handsBackToPanel()` return false, so the import releases its window and routes in place as the base did, failed at `expectHandedBack` with `{"windowOpen":true,"record":null,"panels":0,"handbacks":[]}`.
- `toolbar-panel.test.ts` passed whole on Firefox at retry 0 (7 of 7, test 6 included, 179 s). Test 6's driver now reports `"closed"`, and the hand-back assertion is shared by the contacts card, the import and the restore (`expectHandedBack`).
- Capture spec, first try: the unlock-method change never reached the panel. The cause was the scratch spec, not the product. Its privileged panel reads started during the window's passkey step, and a privileged call focuses a browser window, which refuses a prompt starting in another window (FIREFOX.md, toolbar-panel row). A diagnostic run that read only from the control page saw the whole ending: the window closed, the record was written and consumed, and the panel showed Settings with "Now unlocks with your passkey". The fix was to wait for the panel from the control page first, and to use the suite's own readiness (session checked, no boot banner, service ready) before routing the panel.
- The Firefox and Chrome smoke suites run once, on the final head after the review loop, because that loop can change the code they prove (the post-implementation gates).
