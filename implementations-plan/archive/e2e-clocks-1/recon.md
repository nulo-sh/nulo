## How the two clocks run

- **Incoming scanner** (`src/wallet/services/incoming-transfer/service.ts`). One `setInterval(pollIntervalMs)` per note target (network, account) and per public target (network, contract), installed together; the install run (`poll(true)`, `:1154`) fires at unlock, token add and rebuild. Every 4th tick is forced (`FALLBACK_EVERY_TICKS`, `:59`). A tick reads the network's tips once, cached for `SHARED_TIPS_TTL_MS = 5_000` after the read settles (`:1259-1261`): a tick period at or under about 5 s plus the read's latency reuses the last tick's tips and skips. The note arm skips when the proposed block hash has not moved (`:1519`), the public arm when the checkpointed hash has not (`:1229`). The failure backoff (`scan-health.ts:17`, 30 s doubling to 5 min) and the stall rule (10 min) are time-based, not tick-based.
- **Finality read.** `TransactionService.runWorker` loops every 1 s (`service.ts:400-419`); `collectFinalityDue` reads a row whose `finalityNextCheckAt` has passed and re-arms it at `now + FINALITY_READ_INTERVAL_MS`; the first read comes one full interval after the mined commit (`:569`). `SendCheck` ticks every 5 s (`SEND_CHECK_TICK_MS`); after it writes a mined answer it reads again at its next tick (`readOnce`, `:150`), and only an unsettled finality answer waits `FINALITY_READ_INTERVAL_MS` (`:272`). A worker restart makes `TransactionService`'s awaiting rows due at once (`:149`).

### Node calls

| Event | Calls |
|---|---|
| Idle incoming tick (no fallback) | 1 `getChainTips` per network, shared by every target |
| Incoming tick after a new block, per public target | about 3-4 (class gate on a new checkpoint, one ancestry witness, 1-5 log pages) |
| Incoming tick after a new block, per note target | `getNotesRaw` through the PXE (its own sync), one `getBlockTimestamp` per new block |
| Finality read, per awaiting row | 1 (`unsettled`), 2 (`final`), 3 (`pruned`/`moved`) |

At a 10 s tick an idle network costs 6 tips reads a minute instead of 2. The cost that matters on a loaded shard is the PXE: a note scan syncs it, and other work in the same file queues behind it. That is measured, not estimated (plan § Measurement).
