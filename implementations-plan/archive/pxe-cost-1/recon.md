## #1038: the unlock and the public scans

- **The unlock RPC awaits no scan.** `ProfileService.unlockProfile` (`WS/profile/service.ts:747-814`) opens the session inside the facade lock; `onActiveProfileChanged` handlers are dropped promises (`packages/wallet-core/src/utils/event-handler.ts:47-60`). `hydrateSchedulers` (`IT/service.ts:1037-1057`) begins with `getActiveProfile()`, which takes the same facade lock, so the scans start only after the unlock's session write. The unlock touches no PXE call (searched `PxeServiceClient|registerAccount|clearProfileState|provisionChainStoreKey` in the profile service, the session manager and the integrity coordinator).
- **What the probe's "unlock returns" measures.** `ensureUnlocked` (`apps/extension/tests/e2e/fixtures/auth.ts:102-290`) polls `chrome.storage.session` from the popup every 200 ms until a newer session record appears. The record is written before the scans start, so a 19.8 s "unlock" means the popup did not see it for 19.8 s: the reader is starved, not the writer. The popup's own bootstrap (`useProfileBootstrap.ts:85-242`, ending in `getActiveProfile()` before `isLogined`) queues the same way.
- **Shared resources the scan wave saturates** (each a candidate; the issue's "what the unlock waits on is not recorded" still holds):
  - the profile facade lock (`WS/profile/service.ts:144`, FIFO `Lock`): every scan takes it several times (`getNetwork` twice, `getPxeGeneration` per PXE request, `outbox.drain`'s `activeProfile()`), and so does every popup RPC;
  - extension API traffic: each PXE request is its own `chrome.runtime.sendMessage` (`packages/extension-messaging/src/offscreen/client.ts`), and each `pollPublic` ends in `outbox.drain()` with a whole-namespace `listOutbox` read (`IT/balance-outbox.ts`);
  - the PXE chain guard (`packages/wallet-core/src/utils/rw-guard.ts`): public reads share it, a queued writer (the note arm's `getNotes`) blocks new readers;
  - the offscreen health ping (`apps/extension/src/wallet/utils/offscreen.ts:349-356`): a missed 3 s PONG recreates the document.
- **The burst recurs after the unlock.** All public targets install within 4 ms (`commitSchedulers`, `:1097-1121`), so their 30 s intervals (`DEFAULT_POLL_INTERVAL_MS`, `:53`) stay in phase: every new checkpoint, and every fourth tick (`FALLBACK_EVERY_TICKS`, `:57`, forced), starts every target at once again. Every rebuild (token add or delete, account add, profile change: `:1362, :499, :1393-1399, :457-459`) re-fires every first poll. `retryIncomingScan` (`:1308-1318`) starts every target of the network at once.
- **A first poll can already be lost.** `pollPublic` returns on `publicPolling.has(key)` before its epoch check (`:1195`): a rebuild that lands while the old scan of the same key runs drops the new install's kick, and the next try is the next interval tick (plausible but unverified as a user-visible delay; at most one interval).
- **Pins a gate must keep:** `service.scenarios.test.ts:2332` (interval registered before the first poll), `:2375` (an old interval during a rebuild scans nothing), `:6493` (no tick before 30 s), `:6502` (one tips read serves every target of a tick); network `incoming-public-transfers.test.ts:122-152` (a receipt sent while locked shows within one 10 s e2e interval of the unlock). No test covers more than two tokens.

## #1033: the private balance read

- **Mechanism holds.** `balance_of_private` is `private_balances.at(owner).balance_of()` (aztec-standards `token_contract/src/main.nr:409-410`), `Owned<BalanceSet>` at storage slot `0x7`; `BalanceSet::balance_of_with_offset` sums `UintNote.value` page by page, 10 notes a page (`MAX_NOTES_PER_PAGE`), status ACTIVE, owner set by `PrivateSet::view_notes` (`balance_set.nr:27-46`, `private_set.nr:364-367`). The PXE's `getNotes` reads every note of the contract through its only index, `notesByContractAddress`, and filters owner, slot, status and scopes in memory (`PXE/storage/note_store/note_store.ts:105-196`): one read is one walk, and the utility does about N/10 walks.
- **A wallet-side read would cost one walk.** `PXE/debug/pxe_debug_utils.ts:78-103`: the debug `getNotes` runs synced, calls `ensureContractSynced`, then the same `noteStore.getNotes`. With `{contractAddress, owner: account, storageSlot, status: ACTIVE, scopes: [account]}` it returns exactly the notes the utility sums, at the same anchor discipline (`PXE/pxe.ts:1294-1320`). It is the scanner's cost class: about 2 s at 900 notes on the loaded host (#1033's table), against 11 s.
- **What a wallet-side read must match** (each would make the two diverge): the owner filter (the scanner's read has none and would over-count notes in a shared scope); the slot (per class); ACTIVE status (`NoteDao` carries no nullified flag, so it cannot be filtered after an ACTIVE_OR_NULLIFIED read); a note that does not decode must fail the read, never be skipped; u128 overflow fails the contract call (unreachable for a real supply); reads at two anchors can differ, so a parity check pins one synced block.
- **Scope of classes.** The read target is discovered by ABI scoring (`WS/token/functions/descriptors.ts:91-124`), so a user-added token runs whatever its `balance_of_private` does. A wallet-side sum is exact only for a class whose bytecode the wallet pins: the class id hashes the bytecode, so its utility's semantics cannot move. `note-schemas.ts` keys the two Token classes by catalog class id; a token row's `classId` field (`WS/token/spec.ts:23`) is optional and not a proof.
- **Locking.** `getNotes` and `executeUtility` both take `withPxeWrite`; `executeUtility` alone goes through `withStaleAnchorRetry` (`pxe/service.ts:491-493, 589`). The block stream swallows a failed sync for both (`archive/incoming-transfers/lessons/phase-3.md`).
- **Composition layer.** `apps/extension/tests/COMPOSITION-TESTS.md` D2 (no assertion on `executeUtility`'s result) and D4 (no modelled note state) forbid a composition test of parity; the lane brief's "composition test" cannot hold as written. Parity is network-e2e; the read's filter and decode are unit-testable.
- **No "unchanged" signal exists** per (contract, account): `NoteStore` exposes no count or version; `getSyncedBlock` is chain-wide.

## #1034: senders

- **Paths that register a sender:** the contacts import, rows flagged `isSender` only (`useContactImportExport.ts:~335-345, 388, 401`), on the active network only, no total; the Advanced Senders page (`NewSenderPopup.vue:66`); a dApp's `aztec_registerSender` (32 per app, 128 per chain, `registration-allowance.ts:7,14`, counting calls, not refunded by a delete); a full-backup restore (64 per network, `account-state/normalize.ts:15-33`); a legacy `register_sender` operation that bypasses the dApp allowance (`WS/execution/service.ts:1010-1011, 1112-1115`; no producer found, not proven dead). Adding a contact by hand, a send, and an incoming transfer register nothing.
- **Storage.** The PXE's own `senders` map in the per-(profile, chain) OPFS store, keys only (`PXE/storage/tagging_store/tagging_secret_sources_store.ts`); no wallet copy, no timestamps. A chain purge loses them; only a restore re-adds. "Oldest evicted" therefore needs a new persisted wallet registry.
- **What an unregistered sender loses.** The PXE's default strategy is the non-interactive handshake (`PXE/hooks/resolve_tagging_secret_strategy.ts:43`), which a recipient discovers without knowing the sender (the HandshakeRegistry's `sync_state` scans a tag from the recipient alone); the wallet installs no strategy hook. Only a sender whose wallet tags with `address-derived` secrets is invisible unless registered. Pinned live by `network/receive-unregistered.test.ts`. The archived `contacts-sender-decouple` plan made contacts never touch sender state except the import.
- **Registering a sender wipes the PXE's contract sync cache** (`PXE/pxe.ts:768-771`), so a register-on-send would re-sync every contract under the write lock.
- **Measured cost** (pxe-limits-1, `archive/pxe-limits-1/lessons/phase-3.md`): private-log tags per block = 84 × (watched tokens + 1) × scopes × (senders + own accounts) + scopes + 86 × handshakes, plus one public tag per watched token; 0 / 32 / 128 / 1,000 senders: 170 / 5,546 / 21,674 / 168,169 tags, first PXE call after a block 0.83 / 5.1 / 15.1 / ~71 s (Chrome, load1 162-206); 128 on Firefox 8.7 s (load1 47).
