## #319: the lock route after a password change

- **The click** (`src/composables/useLockWallet.ts:97-120`): returns if not logged in; snapshots `sessionChanges`; awaits `readForLock()` (`getSessionHandle` and `refreshInFlight`, raced against a 3 s budget); returns silently if a profile event or disconnect moved `sessionChanges`; otherwise `lockWallet(handle)` sets `isLogined = false` and fires `lockActiveProfile(handle)` unawaited (`:46-50`).
- **The background** (`src/wallet/services/profile/service.ts:919-944`, `session-manager.ts:397-445`): under `runExclusive`, `close()` clears the in-memory session and emits `onActiveProfileChanged(undefined)` first (`:413-417`), then deletes the session record and clears the lock alarm. That order holds only while the worker holds the in-memory session: a restarted worker's `close()` emits nothing, and `lockActiveProfile` emits its fallback event after the delete and the read-back (`service.ts:934-942`). So a test that sees the record gone knows the lock event was posted earlier only on the in-memory path.
- **The popup** (`app.vue:200-225`, `locked-state.ts:46-53`): each profile event takes `seq = ++profileEventSeq`. The lock event seals (closes popups, bumps the epoch, `isLogined = false`, clears activity and in-flight rows), awaits `getProfiles()` (a 60 s client RPC; a rejection lands on the cached list), returns if a newer profile event arrived, then calls `router.push("/popup/auth")`, unawaited and uninspected (`app.vue:190`).
- **What a landing waits on**: the `getProfiles` round trip; the global guard (`route-guard.ts`: `earlyDecision` bounces `/popup/auth` to `from` only while `isLogined` is true; `lateDecision` awaits `getProfiles` only when `appStore.profile` is unset); vue-router commits the hash only after the guards and the lazy `auth` route chunk resolve.
- **The password change** (`change-password.vue:66-83`; `service.ts:1139-1195`, `:1118`; `session-manager.ts:285-380`): the background reseals, re-keys, then reopens the session, which emits a non-null `onActiveProfileChanged` (the popup's `bootstrapActiveProfile`, `useProfileBootstrap.ts:148-179`, runs networks, accounts, transactions, then re-reads the active profile before setting `isLogined`). The page then toasts and calls `router.back()`. That bootstrap can still be running when the test clicks the lock.
- **Paths that would lose the route**: (L1) a non-null profile event after the lock event, so `isCurrent()` drops the landing; (L2) `isLogined` set true between the seal and the push, so the guard bounces it; (L3) the push cancelled or aborted by another navigation; (L4) the lock event emitted while the popup's profile port is down (a reconnect's `loadProfile` routes only from an auth-required page, `lock-landing.ts:46`); (L5) the route lands and then leaves (`auth.vue:45-47` runs `router.go(-1)` while `isLogined` is true). The recon agent dismissed L2 because "responses and events share one port in order". The plan audit (Opus O3) showed that premise false, and the planner verified it: the background posts a queued `lockActiveProfile`'s event about three microtasks after the mutex handoff, before the response of the `getActiveProfile` read that held the mutex just ahead of it (`packages/wallet-core/src/utils/lock.ts:104-122, 133-172`; `service.ts:285-287, 496-503, 919-929`; `packages/extension-messaging/src/core/base-service.ts:112-118`). A `refreshSession()` fired by the route commit after `router.back()` (`app.vue:415-420`) can hold the mutex and queue both. The bootstrap's `isLogined = true` (`useProfileBootstrap.ts:174`, and `:202`) carries no profile-event fence (`popup/profile-bootstrap.ts:19-29` fences only the failure record), so L2 is open and is the plan's leading hypothesis.
- **The helper's history**: until #313 the helper reloaded the popup when the hash lagged, citing "a stale post-password-change `bootstrapActiveProfile` flips `isLogined` back to true AFTER the lock". e2e-followups-3 made it observational and recorded that race as guarded in product. #319 is the first red of the observational helper on this test, and the guard recorded then covers only a re-read that runs after the lock (L2 above).

## #322: the Firefox capability window

- **The chunk**: `creator-DQZXbG1H.js` holds `@codemirror/state`, `style-mod`, `@codemirror/view`, `@codemirror/language` and `src/components/JsonViewer/creator.js` (no imports of its own; lines 1-5 are `@codemirror/state`'s text, change, facet, state and range-set code, line 5 ends in `style-mod`'s `StyleModule` constructor with its recursive spec renderer). Its importers are `JsonViewer-*.js` and `logger-*.js`.
- **Every popup page loads it**: `dist/firefox/src/popup/index.html` names `popup-*.js`, `JsonViewer-*.js` and `creator-*.js` among its 131 module scripts; the import path is `PopupManager.vue` → `DataViewerPopup.vue` → `JsonViewer.vue` → `theme.js`, whose module scope calls `createTheme(...)` (`EditorView.theme` and `HighlightStyle.define`). So the discover/verify window and the capabilities window, not only the JSON and logger windows, evaluate this code at load. The issue's "shared by the JSON viewer and the logger window" holds for the chunk graph but understates its reach.
- **The wait**: `grantCapBundle` (`tests/e2e/fixtures/extension.ts:479-496`) arms `waitForPopup(ctx, "capabilities", 60 s)` before the click; `waitForPopup` (`fixtures/popups.ts:18-52`) matches a page target whose URL holds `#/windows/capabilities` and was not listed before. Firefox's seam polls `browser.targets()`.
- **Ways a window goes unseen** (`FIREFOX.md` rows and the seam): (W1) Firefox announces a new top-level context only through its first browsing context and filters its replacement, and a `windows.create` window kept its first context 50-70 ms in an idle probe; (W2) `watchForSilentCloses` reports a context closed after 8 consecutive reads that do not list a never-listed handle, which removes the target from `targets()` even if the window lives; (W3) the background never created the window; (W4) the target exists but its URL never leaves `about:blank` in Puppeteer's map.
- **The relay cannot report some of these**: it drops a record whose top context is gone or has no BiDi id (the background page and its frames). For a window BiDi never announced it still resolves an id (`NavigableManager.getIdForBrowsingContext`, `firefox-page-errors.ts:201-214`) and emits, but Puppeteer has no context for that id, so the error reaches no array. The failing test threw before any `pageErrors` read, and `waitForPopup` attaches no error listener to the window it waits for.
