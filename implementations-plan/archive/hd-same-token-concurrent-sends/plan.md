# Back-to-back sends that share chain state

## Outcome

- **Date**: —
- **Status**: completed.
- **Shipped**: A send sequencer that holds a popup send until the earlier sends it shares chain state with are included (`apps/extension/src/wallet/services/execution/send-sequencer.ts`), the execution slot for every Send-page send, and a queued state on the Send page and activity card instead of a failed estimate.
- **Open items**: confirming a queued send at once and estimating it when unblocked, dApp-send ordering, three questions with working answers, residual windows that fail as before and the advisory chaos jobs, tracked in #217, #218, #219 and #220. The fee-method click that might not take is done: a row mid-read now shows as loading (#39).
- **Seeds retired**: none; this record carries no seed prompts.

## Decision

Order sends that share chain state, never fail them: a send that shares state with an in-flight send of the same account waits in the service worker until the earlier one's receipt settles, and a send that shares nothing is not slowed. The owner chose a wait in the service worker that the page only shows, the queued row and its copy, and the per-(profile, chain) execution slot from build to submit for every outgoing transaction, as dApp sends already took it: a backstop for shared state no key names. Popup transfers had skipped the slot under a rule that named no hazard. The dependency wait comes before the slot, never while holding it, so an unmined transaction cannot stall unrelated sends.

Rejected: retrying on the race's error, which waits only after a refused send has paid for its proof and, since the node replaces a conflicting transaction by fee, could evict the first; a blocking estimate wait in the service worker, which would hold an admission slot for minutes and outlive the popup; the slot alone, which releases at submit, the very window that fails; a token-wide key, which would order sends of one token to two recipients that share no sequence; and reading the PXE's tagging store, exact but a new runtime surface, where history errs only toward waiting. Out of scope: fee juice with claim, since a claim is consumed once, and two public spends that together overdraw the balance.

## Why

The standard token delivers private notes with constrained delivery. A transfer uses the recipient's sequence when the recipient gets a private note and the sender's own change sequence when it spends private notes; public to public uses none. The PrivateFPC spends the payer's private fee-juice notes, and an account's first transaction emits its initialization nullifier, both shared across tokens. Nothing ordered popup sends, so a send estimated after an earlier one was proved and before it was mined failed on an unknown nullifier, which the Send page showed as a failed fee estimate, and two sends consuming one shared note or nullifier were refused with a nullifier conflict.

## What shipped

- **Keys** (`apps/extension/src/wallet/services/execution/transfer-sequence-keys.ts`). `seq:<token>:<target>` per delivery target; `handshake:<target>` until the wallet's history holds a mined, successful delivery of that token to that recipient (change is no evidence: an exact spend makes none); `fpc:<address>` for any fee contract but the protocol sponsor on that chain; `init` until the account has a mined, successful transaction there. A pending transaction known only from its record holds its sequences, first-use handshakes and `init`; a call in it with no transfers holds every sequence of its contract and counts it as a fee contract.
- **Sequencer.** Scoped by chain and account, first in first out by a synchronous `enter`. A sent transaction holds until its receipt leaves Pending, in a block or dropped, for at most `SUBMITTED_HOLD_MS` (10 minutes) after it reached the node, or after its row was created when only the row is known: a policy limit, past which a successor runs unordered and the chain still refuses any real conflict. Losing the local record is not a settlement. A send waits at most `MAX_WAIT_MS` (60 minutes, inside the lane's 90-minute heartbeat lease) for its dependencies and the slot together, then fails with "An earlier send of this account is still in flight".
- **Send path** (`apps/extension/src/wallet/services/execution/transfer-executor.ts`). The journal row starts `queued` when the send must wait, heartbeated so the reaper never fails it. It then takes the slot in its own popup bucket, gives it back and waits again if a re-check finds a dApp transaction that reached the node meanwhile, and claims `queued` to `pending`; a cancel that landed first wins. `onSent` fires as soon as `node.sendTx` resolves, before bookkeeping that can throw. dApp sends hold their recorded keys until their receipt settles, and every send that reaches the node bumps an epoch the estimate-reuse stash records, so a build from before it is never reused.
- **Estimate.** It never waits in the service worker: it answers `queued` while blocked or while the slot is busy, else reserves its keys and takes the slot only if nobody holds or waits for it, holding both while it simulates so no proof slips between its simulations. The popup asks again every 2 s (`apps/extension/src/utils/estimate-when-clear.ts`). The fee row reads "Queued behind your previous send" with Send disabled until the real estimate lands (`apps/extension/src/popup/components/modules/send/FeeCostReadout.vue`), the activity card shows "Queued..." with Cancel, and account and network switches stay refused while the send waits.
- **Proof.** `apps/extension/tests/e2e/network/same-token-concurrent-sends.test.ts` runs thirteen cases on Chrome and Firefox at retry 0: four pairs that must not wait, five colliding pairs, a send queued across a closed popup, one cancelled while queued, a send behind a proving dApp send, and an account's first two sends right after a backup import. Its hold changes block production for every file sharing the node, so it runs in a dedicated CI job. A seeded chaos run (`apps/extension/tests/e2e/network/send-chaos.test.ts`) runs nightly with a replayable seed. The slot costs about 0.9 s of a proverless send confirmed beside another, roughly one proof with a real prover.
- The register-on-demand retry of [hd-import-handshake-loss](../hd-import-handshake-loss/plan.md) runs inside the op that names the scope, so a send holding the slot registers its own account without a second slot (`apps/extension/src/wallet/services/execution/transfer-slot.scope-retry.test.ts`).

## Lessons

### note-index

On Aztec 6.0.0-rc.1, constrained delivery orders sends per (token, sender, recipient) sequence: a send at index `i > 0` proves that the nullifier of `i - 1` exists, and index 0 creates or validates the pair's handshake in the one HandshakeRegistry, a note every token shares that each use nullifies and recreates. So a pair's first send uses the handshake whatever the token. The PXE takes a note's index, the highest pending one plus one, when it proves, and proving re-executes the private code. A second send simulated after the first was proved and before it was mined reads a nullifier the chain does not have yet (`reading an unknown nullifier`), and two first sends of different tokens to one recipient collide (`Nullifier conflict with existing tx`).

### mining-hold

The local node's admin API leaves a lone submitted transaction unmined until a second arrives (`nodeAdmin_setConfig` with `minTxsPerBlock: 2`), so a test can stand in the in-flight window (`apps/extension/tests/e2e/fixtures/mining-hold.ts`). Check that the node has no pending transaction before each case and restore the value read before the hold, or a held send pairs with the next case's and mines at once, turning a red case green. An unheld chaos run passes even on the unfixed code: the held matrix is the gate.
