## Facts the plan rests on

1. Establishment resolves `true` once the verify window is navigated or created, not answered (`session-established.ts:180-189`). `needsVerification = isNewConnection || !dappSession.trustedVerification` (`:180`).
2. `onWalletMessage` computes the establishment gate on arrival; the queued row (top-level `sendTx` only) is created on arrival behind it; execution awaits the same gate behind the baton (`background.ts:486-610`).
3. `onSessionEstablished`'s returned promise is awaited by tests (`background.admission.test.ts` `establish()`, `background.connect-window.test.ts` `boot().establish`): folding the hold into it would hang them; upstream does not await it.
4. The verify URL carries the ROW id as `sessionId`, the session's own `verificationHash`, and `isReconnect` (`session-established.ts:73-77`). One row serves every transport session of `(origin, chainId, profile)`, so the row id cannot name the channel to release.
5. `verificationHash` is 64 lowercase hex characters: HMAC-SHA-256 of a fixed string under a key derived from the ECDH secret, hex-encoded (`crypto.js` `deriveSessionKeys`, `arrayBufferToHex`). The wallet generates a fresh key pair per key exchange, so two sessions never share one.
6. Upstream `terminateSession` posts `SESSION_DISCONNECTED`, deletes the session, calls `onSessionTerminated`, and restores the discovery to `approved`, so the same id can key-exchange again with a new hash.
7. The dApp side: `ExtensionWallet.postMessage` has no per-call timeout; it rejects in-flight calls only on disconnect or after 300 s with no inbound traffic, and while a call is in flight it PINGs every 5 s, which the background answers in `handlePing` independently of message processing (`extension/provider/extension_wallet.js`, `types.js` `DEFAULT_HEARTBEAT_DEAD_AFTER_MS`). `pending.confirm()` is local and instant (`manager/wallet_manager.js:208`).
8. A LOCK tears no channel down (`profile-switch-teardown.ts` header and `wireProfileSwitchTeardown`); a profile switch ends every channel stamped to another profile.
9. A lock reroutes every open extension page, the verify window included, to `/popup/auth` (`popup/locked-state.ts` `land()`, `app.vue:201-223`); the verify page unmounts, and after unlock the window lands on `/popup/general`, because only `useDappApprovalWindow.start` sets `pageAwaitingAuth` and the verify page does not use it. So after a lock the check cannot be answered in that window. A verify page that mounts while locked closes itself (`getDappSession` throws, `verify/index.vue` catch). The execute and capabilities windows reject on lock instead (`useDappApprovalWindow.ts:114-116`).
10. While locked, `getDappSession` and `setTrustedVerification` throw `"Invalid id"` (MAC view hides the row); `refuseVerification` still works (raw rows).
11. A queued row is vouched at most `MAX_QUEUED_WAIT_HEARTBEAT_MS` = 90 min (`execution-lane.ts:108`), then the reaper fails it as `stuck_queued` after its 10-min queued grace ("Stopped before broadcast"). `claim-helper.ts` creates a fresh row for a reaped id and throws 4001 for a row in any stage but queued or pending (a person can cancel a queued row from Home).
12. Failure kinds and their copy (`queued-journal.ts:285-292`, `utils/journal-state.ts`): `wallet_refused` reads "Refused before sending" / "The wallet refused this request before anything was signed. Nothing was sent."; `session_ended` reads "Stopped when the wallet locked" / "The wallet locked while this was in progress."
13. Today a send whose session ends while it waits behind the FIFO reaches the identity guard and files `wallet_refused` ("Session no longer valid — reconnect" as its message).
14. The playground has no spinner, but a call in flight shows as a `pg-result` row with `data-status="pending"` (`apps/playground/src/main.ts:70-80`, `lib/log.ts`); its status reads `connected` right after its local confirm.

## What existing tests do under a hold

- Every `dappConnected*` fixture presses They match before the first call (`fixtures/extension.ts:391-428`, `connectPlayground` → `approveVerify`), so they are unaffected.
- `reconnectPlayground` (`fixtures/send.ts:14-26`) races the verify window against `connected` and may send `requestCapabilities` with the check unanswered; it passes today only because nothing is held. Callers: `network/inflight-call-background-death.test.ts:105`, `network/firefox-background-restart.test.ts:32`. Both reconnect an untrusted row.
- `background.connect-window.test.ts:540` ("a sendTx arriving while the check loads is journaled and dispatched once it shows") and `:551` (the batch after it) assert dispatch without a confirm.
- `popup/windows/verify/index.window.test.ts:195-202` pins the exact call log of They match.
- No test covers: a call while the check is open, closing the check without an answer, a trusted reconnect dispatching at once (the transport test at `background.transport.test.ts:200` asserts only decryption), a lock with the check open.
