- **The search case as first written passed on base.** F3 opens the panel at the bottom, which shrinks the scroller and leaves the view 28 px off the end, so CodeMirror's 4 px band never applies. The at-the-end search hold is: panel open, a scroll back to the end (which resumes the follow), then focus back into the search field. - **D3a needs one snapshot per CodeMirror measure.** With a snapshot on every held line, a burst through a trim moved the view 1 075 px (chunked variant) and 1 818 px (final test, rule removed). Cause, traced in `@codemirror/view` 6.43.9: `scrollSnapshot()` reads `scrollDOM.scrollTop` against the view's height map; after a trim's dispatch the height map is already trimmed but nothing has re-measured, so a second snapshot in the same frame anchors 100 lines too far down, and it replaces the pending one (`EditorView.update` maps a pending scroll target through later transactions, `index.js:7994-8007`, but a new `scrollIntoView` effect overwrites it). Fix: while a snapshot is pending (cleared by a `requestMeasure` read in the measure that applies it), later lines carry no effect and CodeMirror maps the pending one. Local to `onLogAdded`; no new state outside the component.
- **D3a alone, trim on the first held line (the plan's case):** Chrome green by a hair (the restore left the gap at exactly 20 px, and the re-arm test is `< 20`), Firefox red (button gone: the follow re-armed, I2 confirmed).
