- **History.** Nightlies 26280 and 26281 (2026-10-07, 10-08) and stable v0.30.2 were published before the draft flow and before the ruleset; 26282 is the first release through the draft flow, and the 10-10 and 10-11 nightlies failed before publish (#308 is the open cause of the 10-11 one).
- **The community record of the cause.** Several reports from 2026-08 to 2026-10 describe the same behaviour: a REST `PATCH` of a draft release that omits `tag_name` resets it to `untagged-…`. One reproduced it with an A/B on the same draft (a PATCH without `tag_name` → `untagged-424b6044…`; with `tag_name` → kept): [marcandreuf/memship#94](https://github.com/marcandreuf/memship/issues/94). Projects fixed it by restating `tag_name` in every draft edit, the notes write and the publish alike: [nwarila-platform/workflow-container-factory#7](https://github.com/nwarila-platform/workflow-container-factory/pull/7) sends the tag; [starhaven-io/Brewy#390](https://github.com/starhaven-io/Brewy/pull/390) sends the tag and `target_commitish`. GitHub's own CLI does the same on every `gh release edit`: when the caller names no tag it sends the release's current one, under the comment "If we don't provide any tag name, the API will remove the current tag from the release" ([cli/cli `pkg/cmd/release/edit/edit.go`, `editRun`](https://github.com/cli/cli/blob/trunk/pkg/cmd/release/edit/edit.go)). One report could not attribute its own reset to a PATCH ([xberg-io/actions#68](https://github.com/xberg-io/actions/issues/68)). GitHub's REST reference documents none of this; it says only that `target_commitish` is unused when the tag already exists.
