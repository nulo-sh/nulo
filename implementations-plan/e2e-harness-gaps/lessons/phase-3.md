## 3.1 Multicall nonces (#164)

- **Red on the base playground.** `tx-sendTx-multicall.test.ts` rewritten to read the dApp's `sendTx` result, the record's terminal stage, the mined receipt and the recipient's public balance delta. On the base playground (nonce `i`) both cases fail on Chrome, retry 0: `#32` in 22.8 s, `#33` in 20.8 s, each with `status=error` and the dApp error `"The wallet could not process the request."` (the unclassified constant).
- **The cause, read once from the journal** (a temporary dump in the test, removed before commit): the record is `{ stage: "failed", from: "simulating" }` with `Assertion failed: Invalid authwit nonce. When 'from' and 'msg_sender' are the same, '_nonce' must be zero`. The claim holds, narrower than the issue says: the wallet's own simulation (`simulatePublic: true`) refuses the transaction before proving, so the calls after the first never reach public execution on chain. The old test passed because it accepted a record at `simulating`.
- **The fix.** `buildTransferExec` passes nonce 0 on every call: each call's `from` is the sending account. A single call already had nonce 0, so no other test's input moves.
- **Green, retry 0.** Chrome 2/2 (`#32` 32.5 s, `#33` 27.1 s, file 59.7 s); Firefox 2/2 (`#32` 41.4 s, `#33` 36.7 s, file 78.0 s). Each case sees the dApp's hash, one `succeeded` record, a mined receipt and the recipient's balance up by 3 and 7 units.
- Fast: `bun run lint` 0, `bun run typecheck:all` 0, `bun run test` 0 (734 files, 11,113 tests).

## 3.2 NO_FROM sends (#153)

- **The private-only rule, pinned where it shows.** `tx-request-builder.pins.test.ts`: a NO_FROM call whose selector is a public function throws exactly `DefaultEntrypoint only supports private functions` before any fee read, and a private one builds. Red with the check disabled (scratch edit, reverted).
- **The refusal e2e.** The NO_FROM button's public call: the window shows the fee-set badge, the dApp gets `status: error` with `{ message: JSON.stringify(UNCLASSIFIED_ERROR_MESSAGE) }` (the wallet-sdk carries the envelope as a JSON string, as `SCOPE_VIOLATION_ENVELOPE` in `scope-refusal`), and the one record is `failed`.
- **I1 did not hold.** The sponsored control (`SponsoredFPC.sponsor_unconditionally` on the canonical sponsor, salt 0, registered through `registerContract` under the `transaction-contracts` grant) failed on the first Chrome run: dApp error, record `failed` from `simulating`, cause `stubAccountAddresses: no contract instance registered for <the account>` (read once from the journal by a temporary dump, removed). The concurrent case failed the same way for both sends.
- **Cause.** `TxRequestBuilder.buildNoFrom` calls `ensureRegistered` (keys) but not `ensureContractRegistered` (instance); `discoverNoFromAuthwits` stubs the account, and `PxeService.simulateTx` needs the instance of every stubbed address. Only `NuloAccount.buildTxExecutionRequest` (a standard build) registers it, so any account with no standard build in that PXE store fails every NO_FROM send. Fix in D23; panel in D23-D24; the registration pin is red without the line.
- **Serialization evidence (D25).** Codex showed a single proving + queued snapshot can pass with the mutex bypassed (`queued` is the record's stage from the request's arrival). The case now waits for the second window to close, then holds the pair for 3 s inside the gate window. Measured margin on Chrome: the pair first seen about 0.1 s after the first send entered `proving`, the last read 3.1 s after it, 14.9 s before the gate could release itself.
- **Mutex bypass, once (D-orch-13).** `ExecutionMutex.acquire` returning a no-op release (scratch edit, reverted, `git diff` empty after): the concurrent case red at retry 0 in 82.2 s, `no send held at proving with the other queued; sends: [succeeded, succeeded]`: both sends ran past each other, both parked on the gate, both released by its safety timeout.
- **Not this lane, filed:** `waitForTxMined` (`fixtures/aztec.ts`) returns at `proven`/`finalized` and never reads the receipt's `executionResult`, which is where 6.0.0-rc.1 reports a revert (`TxStatus` has no `success`/`reverted` any more). Fixtures belong to the `e2e-followups` lane. The multicall case does not lean on it: its balance delta is the proof.
