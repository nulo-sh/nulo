The runner logged the reinstall, the four `Verified` pins and `added 1048 packages`; `install.sh`'s `aztec-node` load check passed; the e2e setup reported "Local Aztec node is ready". The run then failed (exit 86) before any test ran: the playground dev server printed its `localhost` URL, but global-setup's 30 s health poll never reached it. Likely cause, environmental: the run lacked the `NODE_OPTIONS=--dns-result-order=ipv4first` that this repo's documented `e2e:agent` invocations set (`apps/extension/tests/e2e/README.md:208`). Retry once with it, on the same lane volumes (the stamp matches, so no reinstall).
- Run 2 (`NODE_OPTIONS=--dns-result-order=ipv4first`, same volumes): the playground now came up, so run 1's cause held. The one test then failed in 175 ms, three tries: "Could not find Chrome (ver. 155.0.8059.79)" under the puppeteer cache. In the container, `bun install --frozen-lockfile` ran no Puppeteer postinstall, so no Chrome exists; CI gets Chrome from that postinstall (`.github/actions/setup-puppeteer/action.yml:5`). The cause is the runner's browser setup, outside this change. Stopped here, after two runs: a third would mean patching the runner's Chrome install by hand.
- Result: the runner proves the install half in full. The changed tree installed from the new lockfile, `install.sh`'s `aztec-node` load check passed, and the Aztec CLI booted the local network twice. The e2e half falls to the PR's two network lanes, as the plan's fallback says. Container and both lane volumes removed; the export handed back and deleted.
