## #865, the lane brief, and what did not hold

- **#865 demonstrated**: `registry.test.ts` checks only registered migrations; nothing compares a stored shape before and after a change. Holds at `60fde7e7`.
- **Did not hold.** (a) "Two fields added to the reset journal": they are on `StaleNetworkView.reset`, an RPC view; the stored `ResetJournalSchema` is unchanged since `v0.31.0`. (b) A 0.31.0 passkey backup is refused with "Incompatible backup" before any passkey prompt (`composables/useFullBackupImport.ts:192`), not "integrity failed". (c) The required `l1ChainId` and the pxe-generation fence hold since the starting commit, so no released row lacks them.
- **Missed by #865.** `ARCHITECTURE.md` § 5 contradicts itself (`:108` vs `:119`) and says bad rows are deleted (they are kept); the engine reads and writes JSON strings only (`packages/wallet-core/src/migration/staging.ts:27,56,71`), so the keys stored as objects or bare strings cannot be migrated today (D9); the "UPDATE FAILED" screen's "Reinstall" advice is reachable at 1.0.0 without any migration: a corrupt or out-of-range `nulo:schema:version` returns non-retryable `needs-recovery` (`migrator.ts:244-249`), which `runtime.ts:409` makes terminal (OA-2).
- **Deviation from the lane brief, both panel legs (D4).** The brief asks every hand-guarded key and the profile rows to read through a zod codec. Their guards carry rules a zod object cannot state (a quote judged by its map key and the clock, `S/price/service.ts:306-318`; a deleted-token tombstone kept beside corrupt fields, `S/token/seeder.ts:118-138`; legal history kept entry by entry, `packages/legal/src/status.ts:110`; pins normalised and capped; a malformed restore outcome deleted), and a profile codec would hide a row that today opens derived-only (`S/profile/service.integration.test.ts:4150`). So those keys keep their read code, the registry describes what is written, and the goldens hold the read code's decoded output fixed. Every key is still registered and snapshotted; #524 stays a closed known limit, with a comment.
- **Only one 0.31.0 → HEAD change leaves old rows wrong**: #692's re-key of received-note rows (#689 A, "no migration; reinstall"). The Testnet reset purges them with the old chain, so P62-02's "no migration for pre-1.0.0 history" holds for every store install on Testnet.

## Outcome & Quality Bar

- **For whom:** a 0.31.0 store user whose wallet updates itself to 1.0.0; every 1.x user after them; the contributor who changes a stored shape next.
- **Excellent:** (1) a PR that changes what a stored value may hold, or how the wallet reads one, fails CI until it registers a covering migration or a reviewed additive mark, and the failure names the shape and both ways out; (2) every row a 1.0.0 build wrote still reads to the same values after every later migration, proven over frozen goldens by the real `Migrator` and the backup migrator; (3) a populated 0.31.0 install opens on the 1.0.0 candidate on Chrome and Firefox, through the Testnet reset, with no barrier and every stored key reading under its registered read code except what the reset purged; (4) a person holding only an unchecked passkey backup is told, before any prompt, how to get back in.
- **Good enough:** a changed predicate or transform body is caught only where a golden exercises it (a known limit, filed at close-out); the update test runs by hand before each promote, not on every PR; the reset is proven over 0.31.0's node-free Testnet rows, not over Testnet history, which no e2e can produce (Phase 4's evidence gap).

## Architecture & Implementation

### Phase 1 (A1) · one registry of stored shapes

- **Module** `wallet/storage/stored-shapes.ts`: `STORED_SHAPES`, one entry per `chrome.storage.local` key family, keyed by a stable name: `{ ref: StorageRef; encoding: "json" | "structured"; schema: z.ZodType; read: "codec" | ((raw: unknown) => unknown); options?: EntityStorageOptions; authenticated?: true; engine?: true }` (`StorageRef` from `@nulo/wallet-core/migration`; a per-profile key is a `root` ref whose keys are `${root}@${id}`). Schemas stay where they live (`S/*/spec.ts`, the repos); the module imports them. Inline roots get exported constants (`nulo:core:dappSessions`, `nulo:journal`, the five `incoming-*`, `nulo:core:token-prices`, `nulo:core:token-list`, `nulo:core:token-seeded`, `nulo:core:active-network`, the UI keys).
- **`read: "codec"`** (the 18 EntityStorage roots with a zod codec and the 7 raw repos on `decodeRow`): the schema is the read code. Factories `entityStorage(name, area)` and `valueStorage(name, area)` build every local store from the entry, its key-identity `options` included (`auth-registry`, `token-balances`, `profiles` carry them today), and the raw repos take `STORED_SHAPES.<name>.schema`. **`authenticated: true`** marks `nulo:core:dappSessions`, whose read is `DappSessionMacStorage`'s MAC check over every field but `mac` (`S/dapp-session/mac-storage.ts`): a schema change that alters what a parsed row holds (a new `.default`, a stripped key) fails every stored session's MAC and deletes it, so R3 reads it through the wrapper.
- **`read: <decoder>`** (D4): `nulo:config`, `nulo:core:token-prices`, `nulo:core:token-list`, `nulo:core:token-seeded@*`, `nulo:core:active-network@*`, `nulo:core:profiles`, `nulo:legal:accepted`, the `nulo:ui:*` keys and `nulo:onboarding:completed`. The decoder is the function the wallet reads with today, exported as a pure function where it is private now (`ConfigStore`'s per-prop merge, the token-list `readState`, the price quote filter; clock-dependent ones take `now`); the schema describes the written shape. Two tests hold it to the writer: `z.output` of the schema and the writer's TS type are exactly equal (an `Equals<A, B>` type assertion, per union variant for `Profile`), and one test drives the real writer (the service method that stores the key) and parses what it stored with the schema.
- **`engine: true`** (D3): `nulo:schema:{version,running,backup,attempts,blocked,degraded,retry-requested}` and the legacy `nulo:core:storage-version`, described, read by their hand decoders (`decodeBlockedStatus`, `isValidRetryRequest`, the migrator's own checks). A migration cannot cover them (R2).
- **The scan** `wallet/storage/stored-shapes.scan.test.ts` (on `scripts/type-roles/source-scan.ts`, the TypeScript scanner for string and template literals, `parseSource` for SFC scripts), over non-test source in `apps/extension/src` and `PACKAGE_SRC_ROOTS`: (1) every literal starting `nulo:` is a registered ref (exact, or `<root>@` + a suffix) or appears in `NOT_LOCAL_STORAGE` with a kind (`session`, `lock`, `alarm`, `message`, `label`, `file-tag`, `e2e`) and a reason; (2) every `useSyncedRef("<key>"` builds a registered `nulo:ui:<key>`; (3) `new EntityStorage(` / `new ValueStorage(` appears outside `wallet/storage/` only with a `storage.session` area; (4) a fixture self-test per rule and a non-vacuous count.

### Phase 2 (A1) · the snapshot, the goldens and the guard

- **Emitter** `wallet/storage/stored-shapes/emit.ts`: `z.toJSONSchema(schema, { io: "input", unrepresentable: "any", override })`, keys sorted recursively, `required` sorted. Input mode because stored bytes are the codec's input. Every node zod cannot express must carry a description (`.describe()`) and is emitted with a marker: `z.custom` (`x-custom`), a refinement (`x-refine`), a transform, pipe or preprocess (`x-transform`), a `.catch` (`x-catch`); an overwrite check (`.trim()`) or `z.coerce` counts as a transform, and the validating output side of each pipe in a chain, which input mode leaves out, is emitted in order under `x-pipe-out`; an unlabelled one throws with the shape and path. Adding, removing or relabelling one changes the snapshot; a changed body is caught only by the goldens (the known limit).
- **Snapshot** `wallet/storage/stored-shapes/snapshot.json`, written only by `bun run baseline:storage` (root script → `apps/extension` script running `scripts/storage-baseline/generate.ts`): `{ stamps: [{ version, zod, shapes: { <name>: { ref, encoding, read: "codec" | "described", options?, authenticated?, engine?, schema } }, migration?: n, additive?: { names, reason } }] }`: everything that decides how a row is read, not only its schema.
- **Goldens** `wallet/storage/stored-shapes/goldens.json`: rows `{ id, stamp, shape, key, raw }`, at least a `full` row (every optional field present) and a `minimal` one per shape, in wire form (the `dappSessions` rows signed by the real wrapper with a fixed test key). Authors write `raw` (seeded once from `S/storage-codecs.test.ts`'s corpus where it covers the store). **Expectations**: each stamp records, for every golden of every earlier or equal stamp, its decoded value after that stamp's migrations (`null` once a migration removes it), written by the generator at a fixed `now` and pinned with the stamp, so a migration's effect on every old row is in its PR's diff.
- **Frozen** ⇔ `PINNED_STAMPS` (hardcoded in `snapshot.test.ts`, the address-freeze pattern) is not empty: one entry per stamp, the SHA-256 of the stamp's canonical JSON and of the goldens it introduced. Nothing in the generated file can turn the guard off.
- **Rules**, `wallet/storage/stored-shapes/snapshot.test.ts` (vitest, in `bun run test`):
  - **R1 fresh:** the last stamp's `shapes` and `zod` equal the emitter's output and the installed zod; its `version` equals the current schema version (`max(BASELINE_VERSION, last real migration)`); the goldens' `decoded` equal the read code's output pre-freeze. Failure text: run `bun run baseline:storage`.
  - **R2 justified** (frozen), per consecutive stamp pair: a `+1` step names the registered migration of that version, whose `reads ∪ writes` covers every changed or removed shape, none of them `structured`, `engine` or `authenticated` (D9: such a change stops for a plan of its own, encoding support or re-signing at unlock, which is the owner's); a same-version step carries `additive` naming exactly the changed shapes and removes none. The restrictions of both stamps apply, and no step may drop `authenticated`, `engine`, a key-identity option or turn `codec` into `described`: a downgrade fails, so removing a flag cannot authorize what it forbade.
  - **R3 old rows still read**, per golden stamp: seed a `memStore` (moved from `registry.test.ts` to a shared test helper) at that stamp's version; run the real `Migrator` over `realMigrations`; decode every row through its entry's real read path (a factory-built store over the `memStore`, so key identity applies; the MAC wrapper for `authenticated`; the decoder for described keys); the result must equal the last stamp's expectation for every golden, row count included. Then rewind the marker and run again: contents equal (idempotency, as `registry.test.ts`'s `runTwice` does). The backup-sliced roots' goldens run through `normalizeBackupData` → `migrateBackupData` → `denormalizeBackupData` against the same expectations. Between consecutive stamps, a shape outside the step's migration footprint keeps every expected path (new paths allowed), so an additive stamp cannot change an old row's value unseen; a migration's own test still asserts its before→after rows (template step 9).
  - **R4 append-only:** every stamp has its pin and matches it; a pin with no stamp, or `goldens.json` changing an introduced block, fails. The generator prints the pin to add.
  - **R5 1.0.0 backups** (from A4): `validateAndMigrateBackup` accepts both pinned backup fixtures (`stored-shapes/backups/`: a plain password backup, a passkey backup with its MAC) up to the passkey prompt, and their slices decode under the read code.
- **Generator** `scripts/storage-baseline/generate.ts`: unfrozen ⇒ rewrite the one stamp and its expectations; frozen and unchanged ⇒ no-op; changed with migration `last+1` registered ⇒ append its stamp; changed with `-- --additive "<reason>"` ⇒ append a same-version stamp; otherwise refuse with both ways out. It never edits a pinned stamp; `-- --freeze` (A4) prints the first pin.
- **Migration helpers.** `template.ts` steps 7 and 9 cite R3; `footprint-coverage.test.ts`'s `SCHEMA_SAMPLES` (contacts only) becomes the registry's schemas and goldens, so a row-map migration on any root is checked.
- **Docs in A1:** CLAUDE.md § Persisted-storage shape changes gains the pre-flip step (a shape change runs `bun run baseline:storage` and keeps the goldens decoding), so the running lanes (tx-record-1's `feeChoice`) re-stamp through it.
- **Result (A1).** The guard's limits, each named in the PR: a service-level row filter beyond its store (the account service's `rowMatchesKey`) is outside the snapshot; a stamp holds one migration, so a PR registering two needs a stamp each; R3's key check fixes each golden's key, so a migration that moves rows to a new key needs that check extended in its own PR; a pin is trusted as reviewed (D22).

### Phase 4 (A3) · the in-place update harness and the 0.31.0 update

- **Harness** `tests/e2e/fixtures/update/`: `releaseBuild(tag, browser)` downloads `nulo-<browser>-<v>.zip` and `SHASUMS256.txt` with `gh release download` into the run-owned `apps/extension/.e2e-state/releases/<tag>/` (D25) and accepts the zip only when its SHA-256 equals the digest pinned in the harness for that tag (reviewed once; 0.31.0's from its release) and the one `SHASUMS256.txt` line naming it agrees. Each run unpacks the checked bytes into its own directory (`.e2e-state/update-<pid>/`). `inPlaceUpdate({ builds, populate, verify })` copies `from` to one fixed extension path P there, launches it behind the egress guard in a session that can reinstall it, populates, replaces P's contents with `to` and reinstalls it in the same session (D21), verifies. A candidate names the commit it was built from, and `updateBuilds` refuses it at any other or over uncommitted build inputs (D28).
- **Candidate version.** `to` is built with a version suffix, as `_build-extension.yml`'s `version_suffix` does, so its `__VERSION__` differs from 0.31.0 and the integrity coordinator re-derives every account, as it will for a real 1.0.0 update.
- **Live scenario** `tests/e2e/network/update-in-place.test.ts`, opt-in with `NULO_E2E_UPDATE_FROM=<tag>`, on a `dev` still on Aztec `6.0.0-rc.3` (0.31.0's line, so the old build syncs with the run's sandbox): through the 0.31.0 build's own UI, a password profile with its default and a second derived account and an imported account on Testnet (the reset's source chain; Testnet is the stand-in node, so these are the rows a person can hold there without a node), two contacts, then an added network on the run's sandbox with an account, a registered token with a received private and public transfer, and a connected playground session. Then it writes the whole `chrome.storage.local` to `tests/e2e/fixtures/update/v0.31.0.storage.json` (test seed and password only), updates, and verifies: no `migration-blocked`, `migration-updating`, `migration-degraded` or `account-integrity-blocked`; every stored key registered and read by its entry's read code; the profile unlocks; accounts, contacts, token, history and network read in the UI; the playground session works. A private receive whose note is unspent reads twice on the sandbox chain, as #689 A decided; the check is that every 0.31.0 row still reads.
- **Replay scenario** `tests/e2e/update-replay.test.ts` (smoke, same opt-in): installs the 0.31.0 zip, writes the recording into it, updates, verifies the same assertions offline (the stand-in node; no chain). When the candidate's Testnet seed id differs from the recorded row's (after the 6.0.0 bump), the Testnet-chain account and imported-key rows must be non-empty before, the takeover must show `network-reset`, and after the reset the test asserts exactly: the derived Testnet accounts re-created with their names and indexes, the imported Testnet account re-created on the new chain with its key resealed (it opens; `resealImportedForReset` makes only an unreadable key unmovable), the old chain's account and key rows gone, the sandbox chain's rows and the contacts kept; when the ids do not differ, no takeover may show. This is A4's gate on the final candidate: a 6.0.0 sandbox cannot serve the rc.3 build, so only the recording can update "through the reset".
- **Mechanism first, before A1's PR opens.** Step 1 runs in this lane's worktree while A1 is built and proves on each browser, with two builds of the current tree, that the swap keeps the id and the storage and that the SW sees `onInstalled` reason `update`. If Firefox cannot under its temporary install, the arc stops and reports: storage-keeping prefs would test a path users do not take.
- **Mechanism result (D21, [lessons/phase-4.md](lessons/phase-4.md)).** Close, swap and relaunch reports `install` on both browsers, so `inPlaceUpdate` swaps P while the browser runs and reinstalls it in the same session: Firefox through the driver's own temporary install, Chrome through CDP `Extensions.loadUnpacked` (a launch mode of `fixtures/browser/chrome.ts`: pipe, `--enable-unsafe-extension-debugging`, no `--load-extension`). Both report `update` with the old version, the id and the storage; verification runs in that session.
- **Evidence gap, stated in the PR.** History, received notes, tokens and a dApp session on the Testnet chain need a Testnet node, which no e2e has (the sandbox serves another chain id, and the wallet refuses an endpoint that does). So the reset is proven over 0.31.0's node-free Testnet rows; that 0.31.0's rows of the other roots read is proven on the sandbox chain; that the reset purges rows of those roots is proven on current rows in-process by `S/network-reset/service.composition.test.ts:328` (it seeds accounts, imported keys, tokens, transactions, authwits, FPCs, the journal and incoming-transfer rows on two chains and checks the old chain emptied, the other byte-identical); A3 adds a focused assertion there for any purged root it does not seed (dApp sessions are checked at `:381`). The purge selects rows by decoded fields, which the first two proofs cover.
- **Failure mode, cheaper layers, runtime.** Rows written by the released code, not by fixtures, read under the candidate through the real boot path (gate, engine, integrity coordinator, classifier) after a real in-place update on each browser. A unit or composition test reads only rows someone wrote by hand. Estimates: live 6 min Chrome, 9 min Firefox; replay 2 min each; measured in A3's gate.
- **Fixes.** Whatever breaks is fixed at its cause in A3; a fix that needs a migration of pre-1.0.0 history is refused by P62-02 and goes back to the orchestrator.

## Security & Adversarial Considerations

- **Threat model.** Stored rows and imported backups are hostile input (CLAUDE.md § Persisted-storage). No read path changes semantics: codec roots read through the same schemas, hand-guarded keys keep their decoders (D4). The new factories construct the same stores; the type-level and goldens checks fail if a factory passed a different schema.
- **Authenticated rows.** `nulo:core:dappSessions` is read through its MAC check; R3 reads its goldens the same way and R2 refuses any migration of it, so no schema change can silently delete every connected session. The MAC rule itself is untouched.
- **What the guard trusts.** A reviewer reading the pins: rewriting history means editing `PINNED_STAMPS` in a test, which the diff shows. A changed predicate or transform body passes the snapshot and is caught only by a golden that exercises it (#935, a closed known limit).
- **P62-05.** A hostile file chooses which refusal it gets (strip the MAC from a passkey body); both refuse, neither spends a passkey prompt, and the new copy claims nothing about the file it cannot check.
- **Supply chain.** No new dependency (`z.toJSONSchema` ships in zod 4.4.3). The harness runs a downloaded release zip only when its SHA-256 equals a digest reviewed into the repo; GitHub's release storage is otherwise trusted, as store reviewers' source is. CI needs no new permission.
- **Gates.** Nothing loosens a gate; the guard adds R1-R5 to `bun run test`.
