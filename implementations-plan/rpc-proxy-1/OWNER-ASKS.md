# rpc-proxy-1 owner asks

One question and ten owner steps. None concerns what a person sees on a surface arc 1 changes: the Testnet endpoint row's new URL is the data change the lane brief already names. Each arc ships without waiting.

## OA-1. Privacy policy § 5.1 after the Testnet default turns keyless (no arc)

- **Surface:** `legal/privacy.md` § 5.1, the paragraph "What the Developer can see: the default Testnet endpoint uses a provider account belonging to the Developer …" (version 1.2.5).
- **After arc 1's release:** no default endpoint uses the Developer's provider account, so the paragraph describes data the Developer no longer receives from a default install. It over-states; it hides nothing.
- **After arc 2's Worker goes live:** § 2's "The one host of mine it contacts by itself, `tokens.nulo.sh`" stays true, since no build references `rpc.nulo.sh`. Its first sentence, "I do not operate a backend for the wallet", is categorical, and the Developer now runs a public proxy built for the wallet, even though no wallet calls it yet.
- **Options:**
  - **A (ships now).** No change until `rpc-fallback-1`, which seeds the proxy as a fallback, sends traffic through the Developer's account again, and rewrites § 5.1 with that change.
  - **B.** A patch version now (1.2.8), replacing the paragraph with: "What the Developer can see: none of the default endpoints uses a provider account belonging to the Developer." `rpc-fallback-1` then rewrites it again.
- **Recommendation: A** for § 5.1: two edits in a few weeks for a sentence that withholds nothing is churn; `BEFORE-LAUNCH.md`'s row on what the dRPC account exposes stays with `rpc-fallback-1`. For § 2, your call before OS-2 attaches the hosts: A reads it as "no backend the wallet uses" (true until `rpc-fallback-1`); B adds now: "I also operate `rpc.nulo.sh` and `testnet.rpc.nulo.sh`, a relay to my node provider that no default setting uses."

## Owner steps (Cloudflare and dRPC dashboards; arc 2's README carries the same list)

- **OS-1. Workers Builds**, Worker `nulo-rpc-proxy`: repository `nulo-sh/nulo`, root directory `infra/rpc-proxy`, production branch `main`, build watch paths `infra/rpc-proxy/**`, build variable `BUN_VERSION=1.4.2`, no build command, deploy command `bun run deploy`, non-production branch builds off. Narrow its build token to this Worker, as for `nulo-subscribe`, and confirm that no other Worker's build token (`nulo-landing`'s preview builds included, `infra/subscribe/README.md` step 3) can edit `nulo-rpc-proxy`: a branch build that can redeploy it can read its secrets.
- **OS-2. Custom domains** `rpc.nulo.sh` and `testnet.rpc.nulo.sh` attached to the Worker. Check that `testnet.rpc.nulo.sh` serves a valid certificate: Universal SSL covers one level below `nulo.sh` only. If the dashboard cannot issue it, the choices are Advanced Certificate Manager or a one-level name such as `rpc-testnet.nulo.sh` (a naming decision, back to the owner).
- **OS-3. Secrets** (after OS-4's caps) on `nulo-rpc-proxy` (Settings → Variables and Secrets, type Secret): `DRPC_MAINNET_URL` and `DRPC_TESTNET_URL`, each the paid dRPC endpoint for its network, key in the path, from **new keys, one per network**, never the key the wallet shipped (a dRPC key may serve every network it offers). They live only there.
- **OS-4. dRPC:** a daily compute-unit cap and a usage alert on each key, before OS-3. Confirm the cap stops traffic rather than only alerting: it is the proxy's only spend ceiling, and a scripted caller can still spend up to it (a known limit the plan files). If it only alerts, leave the hosts detached and say so: a global limiter would be a plan change.
- **OS-5. No challenge** in front of either host: keep Bot Fight Mode, WAF and challenge rules off them, since a challenge page replaces the JSON the wallet reads (as for `tokens.nulo.sh`).
- **OS-6. Acceptance** (the README lists the exact `curl` commands). First, before the real secrets: set `DRPC_TESTNET_URL` to a header-echo endpoint (`https://httpbin.org/anything`), post one `aztec_getNodeInfo` through `testnet.rpc.nulo.sh`, and read the echoed headers: none may carry your IP (`CF-Connecting-IP`, `CF-Connecting-IPv6`, `X-Real-IP`, `X-Forwarded-For`), your user agent or your `Origin`. Then set the real secrets and check: `aztec_getNodeInfo` through each host answers the right chain; a call the node refuses (bad parameters) answers an error body with no part of the key; a preflight with `Origin: chrome-extension://…` answers 204 with the CORS headers; `Origin: https://example.com` answers 403; `GET` answers 405; `node_getNodeInfo` answers 400.
- **OS-7. Rotate the Testnet key** no earlier than 14 days after the release carrying arc 1 is live in both stores. Why 14: the stores' auto-updates reach almost every active install within days, the unlock rewrites the row, and a pending send pinned to the old URL expires within a day (`MAX_TX_LIFETIME`). Then create a new key, set its URL as `DRPC_TESTNET_URL`, and delete the old key. An install that still runs an older build loses its default Testnet node until it updates (Testnet only). Later rotations need no release.
- **OS-8. Ask dRPC** whether they offer a provider-managed endpoint with its own quota cap and per-IP limits that a client can call without a secret. If they do, it would replace the whole proxy (the Worker, its secrets and its rate limit): the wallet would call that endpoint directly, and its key would again be public but capped.
- **OS-9. Workers plan:** confirm the account is on Workers Paid before `rpc-fallback-1` seeds the proxy. The Free plan's 10 ms CPU per request and 100,000 requests per day would cap it (not needed for this lane, where nothing calls it).
- **OS-10. Narrow the shipped key now**, if dRPC lets a key be limited to one network: limit the key the wallet ships to `aztec-testnet` until OS-7 retires it, so a copy of it cannot spend on Mainnet or any other chain meanwhile.
