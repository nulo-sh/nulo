## Assumptions

**Facts** (verified at 5f7da07c5; recon has the citations):
1. The estimate's `onError` opens "Couldn't estimate fee. Try again." for every failure but a held refusal and an app-paid row the person does not pay (`index.vue:227-233`, `:238`); the error reaches the popup as a plain `Error` whose message is the PXE's `SimulationError.getMessage()`, the call stack lost at the offscreen hop (`packages/extension-messaging/src/core/error-response.ts:25-31`).
2. The PrivateFPC raises "Balance too low" and "Amount too low to cover gas cost"; Token raises "Balance too low". **The options' claim that "A needs only the message the popup already receives" does not hold**: the message alone cannot say whose call failed.
3. `resolveNoFromCall` refuses a default-entrypoint call whose selector's ABI function is not private, before simulation, and the preview reaches it (`tx-request-builder.ts:390-394`; `dapp-send-executor.ts:580-592`). Today that throw is a plain `Error`, so the popup shows the preview toast and TRY AGAIN, and Confirm stays enabled.
4. `refusalBound` records only a `ScopeViolationError`; a recorded refusal makes Reject answer the dApp with that refusal's envelope, `SCOPE_VIOLATION_ENVELOPE` for every kind but the registry's, and files Activity as "Not allowed" with the matching explanation (recon). `resolveNoFromCall` refuses every non-private ABI type, `UTILITY` included (`tx-request-builder.ts:392`).
5. The "Leaves your account" block is skipped wherever the `#fee` slot is filled (`OperationCard.vue:463-464`): under a refusal (`index.vue:706`) and in the raised-fee window (`windows/fee/index.vue:262`).
6. `failed[i]` of `useFeeEstimationMap` holds until the key is asked again (`useFeeEstimationMap.ts:33`); the fee snack closes on that re-ask when no other failure stands (`index.vue:239-243`, pinned at `index.test.ts:1828`).
7. A popup send at `submitting` outlives a lock and an unlock (a manual lock cancels the earlier stages; auto-lock waits while approved sends run; recon); lock clears the popup's `dismissed` only in a popup open at the time. `getSessionHandle()` names the open session as `` `${workerId}:${serial}` `` (`src/wallet/services/profile/service.ts:623-631`); the serial is unique within one worker and the worker id names the worker.
8. `hideHint` has one caller, `onboarding/pages/create.vue:244`.
9. An offscreen-built typed error with details already exists: `PxeStaleAnchorError` (`packages/aztec-runtime/src/pxe/stale-anchor.ts:67`, `packages/extension-messaging/src/errors.ts:352`). `walletErrorFromPayload` calls a class's `fromPayload` only where it says so (`errors.ts:711-727`). Journal normalization stores name, message and stack, not `details`; `classifyOperationCatch` and `toWalletResponseError` pass neither new class to a dApp (the Codex audit's trace).

**Inferences:**
- I1. The PXE's `SimulationError` for a private assertion carries a call stack, outermost first (rooted at the account entrypoint), whose frames name the contract and, where known, the selector of each function on the failing path (`FailingFunction`), the request's own call among them. A public failure's original message is the node's halting message with the decoded assertion appended, so the `Assertion failed: ` prefix is not established there, and a public call another call queued is rooted at that call's contract. Phase 1 step 1 logs, for a private and a public failure, `getOriginalMessage()`, the frames' contracts and selectors, before the classifier is written; a failure the rule cannot attribute keeps the toast (a known limit for queued public calls).
- I2. `snack-placement.test.ts:502`'s unfunded public transfer may start reading as an app assertion. Phase 1 step 1 measures it; if it does, that case moves to a fee-path failure (D9).
- I3. A standard token asks for no authorization when the account calls it directly, so a direct transfer and a discovered authorization describe different movements. A registered token is not bound to that: it can ask the account to authorize a call whose caller is the account itself (`decodeAuthwitEffects` signs any request on behalf of the signer, `decode-authwit-effects.ts:76-90`), and summing both rows would count one movement twice (Codex final pass, finding 4). D4 does not rest on a probe of that: a private authorization's inner hash binds its caller, so one naming the account licenses only a call the account makes itself, which the block already reads directly when it reads as a transfer. `accountOutflows` therefore skips an authorization whose `caller` is the account (`DiscoveredAuthwit.caller`, already on the record), with no match on token or amount. It is a display rule: `caller` is the decoded request, not checked against the inner hash, which the block's "what the calls say" reading already admits.

**Asks:** none open. Q6's Activity row changes only as a consequence of C and in existing copy (UI impact). Page 116 (arc 3) and #1644/#1645 (arc 4) are the orchestrator's open threads, not this plan's asks.

### Arc 1, Phase 1: #1619 A, the app's failing assertion under the fee card

1. **Measure first** (not committed). 2. `packages/extension-messaging/src/errors.ts`: `ContractAssertionError extends WalletError` (code `CONTRACT_ASSERTION`), details `{ assertion: string; frames: { contract: string; selector?: string }[] }`. Its constructor bounds what it keeps, so every rebuild path gets the bound: `assertion` a string cut to 1,024 characters, at most 16 frames, the outermost kept (the stack runs outermost first), `contract` only `0x` + 64 hex, `selector` only `0x` + 8 hex, anything else dropped. Registered in `REBUILT_AS` (the generic `new ctor(message, details)` then applies it) and given a row in the inventory test that fails on an unlisted `WalletError` (`errors.test.ts:133-408`). Test in `errors.test.ts` through `remoteErrorFromResponseContent` across two rebuilds (offscreen → worker → popup): the class and bounded details survive; a hostile payload (non-strings, a 5,000-character assertion, 100 frames, a 70-character contract) rebuilds bounded.

Test beside the service's tests with a constructed `SimulationError` whose stack holds real `FailingFunction` objects (an `AztecAddress`, a `FunctionSelector`, one frame without a selector): converted, frames in order; a non-assertion `SimulationError` and a plain `Error` pass through; `message` is unchanged; a stale-anchor-shaped assertion ("RewindableRegister write originates behind…") is retried and ends as `PxeStaleAnchorError`, never `ContractAssertionError`. `error-envelope.test.ts` gets one case: a `ContractAssertionError` reaching a dApp (its own `simulateTx` failing) answers `UNCLASSIFIED_ERROR_MESSAGE`.

## Security & Adversarial Considerations

- **Threat model.** A dApp controls its calls, the contracts they reach (and so every assertion string) and the timing of its requests. The new surfaces render app-controlled text (#1619) and add one session-storage record (#1569).
- **App text in wallet chrome (#1619).** The assertion is the contract author's: "Assertion failed: refund at evil.example" would read as the wallet's advice if unattributed. Mitigations: the fixed attribution "The app's transaction cannot run right now:"; `safeWire` strips bidi and control characters; a 120-character cap; `<bdi>` keeps a right-to-left assertion from reordering the wallet's words; Vue text interpolation, never `v-html`. A dApp can also make the line say anything up to the cap: that is the pick's nature, and the attribution names whose words they are.
- **Attribution cannot be forged by the dApp.** For a private failure the frames come from the PXE's own execution in the offscreen document, and the calls from the stored request; a contract cannot place another contract and selector in the stack. For a public failure the node reports the frames and the text, so a hostile node could forge both; the node is already trusted for every simulation, so this adds no new trust. A failure inside a contract the app's call reached still reads as the app's, which is true.
- **Typed errors at a boundary.** `ContractAssertionError`'s constructor bounds its details (types, lengths, count, address and selector shapes), so every rebuild path does. Neither new class has a dApp envelope: an unlisted `WalletError` still reaches a dApp as the constant, so no internal text leaks outward (a test pins it).
- **Refusal (#1571 Q6).** Classified by class, from the check the send runs, never by text. Confirm is hidden and `approve()` returns while a refusal is held; the worker records the refusal, so a raced approval is refused before any build (`approveInteraction`), and the build refuses it once more as before.
- **Session records (#1569).** One key per dismissed send: a record id in the key, a session key (a worker id and a serial) as the value, no amounts, addresses or profile names; `chrome.storage.session` only; listed in the closed-world scan. A forged record could only hide a toast for the matching session; any extension page that could write it already holds far more.
- **Least privilege, supply chain, crypto:** no new permission, dependency or cryptography.
