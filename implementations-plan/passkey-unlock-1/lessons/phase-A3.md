# Phase A3: the choices

## Deviations from the plan (the tree wins)

- **Service.** `importMnemonic`, `restore` and `finalizeRestore` take a passkey answer beside the password; the new row is sealed under whichever is given, and a passkey seal takes an input no stored row opens under. `changeUnlockMethod(id, current, next)` refuses a password to a password (that is `changeProfilePassword`) and allows a passkey to a new passkey. Its reseal is proved before the write: the replacement must open under its new unlock to the same master, entropy and DEK. A rejected write is read back: the original there rethrows, the replacement there is a change made, anything else is reported as a change. The commit checks it still holds the lock after its last read of the row, with no await before the write. `verifyUnlockCredential` is new (D22): it opens the row with the current password or passkey as the change needs it (slots, pairing, the imported-keys key and its envelope MAC), against a live row byte-identical to its snapshot, opens no session and writes nothing. The page runs it before every prompt that would leave a new passkey, so a wrong password shows "Wrong password" and a degraded profile is refused with no passkey left behind; the change then uses the password that was checked. `UnlockMethodChangedError` (registered in `packages/extension-messaging/src/errors.ts`) is the one typed error the page branches on.
- **Bearer.** `SessionManager.open` lost its passhash presence argument: every open with a DEK persists a bearer unless strict mode is on, whatever the profile's unlock. The silent restore skips a row no unlock opens (retired or unreadable), where it used to skip every passkey row. Its strict-mode recheck moved after the envelope-MAC check, the restore's last await, so a toggle during that check leaves no session.
- **Ceremony.** `PasskeyStep` gains `import`, `restore`, `accountFile` and `unlockMethod`. "Use a passkey I already have" is a `discover` request: a get naming no credential at the new profile's own fresh input, on the page (PATH A) and in the passkey window (PATH B, `discoverKey`). An unconfirmed create is confirmed by the next ask for the same name only when it is a create, never by a discovery.
- **Where the prompts run.** Import, restore, the account file and the unlock method run the passkey card in the page (PATH A); on Firefox's toolbar panel the phrase import, the account file and the unlock method move to their own window first (D15's pattern, `utils/own-window.ts`), as Full Backup and restore already did. Only create keeps PATH B, where the discovery step also runs.
- **Import.** A phrase import runs the import's own phrase checks (canonical words, wordlist, checksum) before the passkey card, so a phrase it refuses leaves no passkey. A declined duplicate warning still leaves the passkey its card made: refusing it before the card would need the service's duplicate check over RPC, a new surface.
- **UI.** The unlock choice is `components/composite/import/UnlockMethodChoice.vue` around `AuthMethodTabs` (D18), shared by both import forms. The reuse link is `components/composite/PasskeyReuseLink.vue`, under the create or import button on Create, Import and Restore; on the popup it takes the prototype's tighter spacing and secondary ink. The account file's passkey path is select, agreement, "Confirm with passkey", the file password, "Save account file"; the answer is held for the profile, network and account it was given for, and any reset drops it; a network switch ends a passkey profile's flow until its file is made; a password profile's flow, and a made file, survive it as before. Its Save-on-Enter answers only an Enter in a field, outside a composition; the agreement step's Enter is the base's and stays. The Lock page's strict-mode description and confirm text are P86-10's for every profile. One type-role exception: the selected unlock tab takes segment's active weight (`scripts/type-roles/exceptions.ts`).
- **E2E.** The phrase and backup forms open on Passkey, so the password drivers pick the Password tab first. `passkey-backup` restores under a passkey; `toolbar-panel`'s passkey backup restores under a passkey in its window.
