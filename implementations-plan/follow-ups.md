Seeding runs with zero interaction, which is why the list and its pins ship in the build (`apps/extension/src/wallet/services/token/default-tokens.ts`). ## Grants and scopes

- **Every other failure before a dApp send is claimed reads "Popup closed early".** `failQueuedForError` files anything but a scope refusal or a schema refusal ("Couldn't read request", since [hardening-2](hardening-2/plan.md)) as `popup_bound` (`queuedFailureKind` in `apps/extension/src/wallet/services/wallet-sdk/queued-journal.ts`), and so does the ended-session path (`failQueuedIfUnclaimed` in `background.ts`): a Terms refusal, a missing capability. Their honest labels are a copy decision, and the Terms case is next in line. From [dapp-grants](archive/dapp-grants/plan.md).
- **A dApp cannot widen a contract-classes grant.** Coverage is type-only (`packages/wallet-bridge/src/dispatcher.ts:719-720`), so a wider request opens no window unless the type was rejected before (`:514`). The answer shows the held classes, truthfully, but the dApp has no way to ask for more; a field-aware coverage rule is a product change for its own plan. From [dapp-grants](archive/dapp-grants/plan.md).
- **Repeated scope refusals pile up in Activity.** Every scope-refused or malformed send leaves one failed row, which the GC never evicts (`apps/extension/src/wallet/services/operation-journal/gc.ts:17-24`, `:127-130`), and the per-session cap of 8 counts only `queued` rows (`apps/extension/src/wallet/services/wallet-sdk/queued-journal.ts:37`, `:176-187`), so a connected app that retries a refused send adds one card per try, with no limit. Cap or merge repeated refusals per session. From [dapp-grants](archive/dapp-grants/plan.md).
- **Classify the selector-binding refusal as a scope refusal (the owner picked this on 2026-10-08).** `assertSelectorBinding` (`apps/extension/src/wallet/services/execution/contract-resolver.ts`) throws a plain `Error`, so the dApp receives the unclassified error and the queued send reads "Stopped before broadcast". As a scope refusal the dApp receives code 4100 and the send reads "Not allowed"; that needs `failureKind` (`mark-failed-unless-cancelled.ts`) and the execution code-channel allowlist (`rpc-cancel.ts`) to carry `ScopeViolationError`, not only a class change. From [security-fixes-1](archive/security-fixes-1/plan.md).
- **A refused dApp call's activity record is titled by the name the dApp claimed.** The History card, the detail title and the Method row read "Balance Of Public" for a call whose selector is `transfer_public_to_public`. Only a refused call can carry a mismatched name, since a call that runs passed the selector binding; titling by the resolved function is a UI change, the owner's call. From [security-fixes-1](archive/security-fixes-1/plan.md).
- **`requestCapabilities` is allowed as a batch leg** and opens a connect window (`packages/wallet-bridge/src/method-descriptors.ts`; upstream `BatchedMethodSchema` includes it). Decide whether it joins `grantPublicAuthwit`, `registerToken` and `sendTx` in the refused set. From [security-fixes-1](archive/security-fixes-1/plan.md).
- **The dApp-session writers read raw stored grants.** The dispatcher's reads project every stored grant, but `apps/extension/src/wallet/services/dapp-session/service.ts` (`holdsCanCreateAuthWit` and the decision writer) and `wallet-sdk/queued-journal.ts` dereference `g.capability.type` on the raw record, and `setCapabilityGrants` accepts unvalidated records from any extension page (its one non-test caller passes `[]`). Hardening them comes first if a malformed grant is ever to self-heal, which the owner declined for now. From [security-fixes-1](archive/security-fixes-1/plan.md).
- **The published schema patch takes any string for `grantPublicAuthwit`'s two addresses (owner ask OA-5, open).** Its content's `caller` and `contract` are `z.string()` (`packages/wallet-sdk-schema-patch/src/apply.ts`), so the dispatch parse accepts any string there; the execution path still validates the addresses it builds from them, and `method` and `args` (unencoded ABI arguments) have no field schema to apply. The address schema would refuse a malformed one at the parse, but it narrows what `@nulo-sh/wallet-sdk-schema-patch` accepts, an npm API change; the recommendation is to ship it in a release that says so. [Record](hardening-2/OWNER-ASKS.md)
- **A schema-valid address can still throw at a `String()` coercion.** `AztecAddress.schema` accepts a Buffer-shaped object, and one carrying an own non-function `toString` passes the dispatch parse and throws at about a dozen coercion sites. The call fails closed, nothing leaks and nothing runs, but the dApp gets the unclassified envelope and the user's log buffer an `error` line per call, where a refusal should be `INVALID_PARAMS` at `debug`. Fix every coercion site, or walk the whole argument tree at the parse. [Record](hardening-2/plan.md) (Arc 1 review, O3)

## Wallet safety

- **The address-keyed fee maps outlive a deleted profile off the live path.** `nulo:ui:feePaymentMethods` and `nulo:ui:sendFeePaymentMethods` hold `{ [address]: … }` (`apps/extension/src/popup/components/modules/send/FeeSettingsCard.vue:335-338`, and `withSendSlot` in `fee-send-selection.ts` beside it). Only the reset page removes them (`apps/extension/src/popup/pages/settings/security/reset.vue:86-88`), after the live delete returns, so the resume and torn-reap paths, and a popup closed mid-delete, keep the deleted profile's addresses. Pruning by address is unsafe, since two profiles can share one, and moving the global wipe onto the other paths changes their behaviour: it needs its own decision. From [wallet-safety-fixes](archive/wallet-safety-fixes/plan.md).
- **An Allow the watchdog displaced mid-un-hide leaves receipts hidden under `trusted`.** After a stall of five minutes or more inside the lock, a displaced Allow with no Block after it stops un-hiding, and only `setTrustAllow` writes `hidden: false` (`unhideLocked`, `apps/extension/src/wallet/services/incoming-transfer/service.ts:658-674`), so nothing un-hides the rest. It is an accepted residual; a `(BUG PIN)` in `service.scenarios.test.ts` holds it. Candidates: re-run the un-hide on replay, or un-hide before the trust write, which needs a `pending` trust row first because the floor skips a contract with none (`:866`). From [wallet-safety-fixes](archive/wallet-safety-fixes/plan.md).
- **A pin or a token-deletion cleanup racing a profile deletion can recreate its pinned-tokens key**, an accepted residual. The purge removes `nulo:ui:pinnedTokens@<id>` on every deletion path, but a popup that has not yet seen the deletion can write it again (`pin` and `onTokenDeleted`, `apps/extension/src/composables/usePinnedTokens.ts:214-243`). A restore that reuses the id then shows those pins (`apps/extension/src/wallet/services/profile/service.ts:1526-1529` frees the id; `operation-journal/service.ts:273-274` says why ids come back); otherwise the key stays as an orphan. Fixes: fence the key by incarnation, or a sweep cheaper than reading the whole store at every background start. From [wallet-safety-fixes](archive/wallet-safety-fixes/plan.md).
- **Two of the token add's compensations delete by id without lock ownership.** `persistToken`'s post-set deletion and network checks (`apps/extension/src/wallet/services/token/service.ts:419-431`) delete `token.id` even when the lock's watchdog displaced the add, so a same-id restore's row can go with it; the last check before `onTokenAdded` deletes only while the add owns the lock. At those two points the row may postdate the purge's snapshot, so skipping the delete can orphan it: the choice needs its own decision. From [wallet-safety-fixes](archive/wallet-safety-fixes/plan.md).
- **Recovery phrase and Change password have no submit latch.** A mouse double-click on Retrieve runs `handleUnlock` twice (`apps/extension/src/popup/pages/settings/security/export/seed.vue:55-67`), and the second `countdown.start()` leaves a 5-minute close that "keep open" cannot cancel (`apps/extension/src/composables/useSecretCountdown.ts:26-35`). Change Password is disabled while loading (`apps/extension/src/popup/pages/settings/security/change-password.vue:229`), so only a same-tick double click reaches it twice. `seed.vue` also has no unmount fence (`full.vue`'s `generation` is the pattern), so a Retrieve that resolves after the page left sets the phrase on the dead page and arms that timer. Since both buttons refuse a repeat Enter, only a pointer reaches either twice. From [keyboard-guards](archive/keyboard-guards/plan.md).
- **Two keyboard focus rings do not show.** The sub-page back arrow is a bare `<button>` (`packages/design/src/ui/SubPageHeaderBase.vue:36-45`) under the base stylesheet's `button { outline: none; }` (`packages/design/src/base.css:270-275`), on every page built on `SubPageHeader` or `CollapsingHeroLayout`, and onboarding's active method tab draws its `:focus-visible` outline in `--nulo-accent` over a fill of the same colour (`apps/extension/src/onboarding/pages/create.vue:231-239`). - **Send's token card has no focus style of its own.** It is a `role="button"` row with `tabindex="0"` and no `:focus-visible` rule (`apps/extension/src/popup/components/modules/send/SelectTokenCard.vue:93-94`), so Tab shows only the browser's default outline, on the failed card's Retry too. It predates send-states; a designed ring is an owner call. From [send-states](archive/send-states/plan.md).
- **A restored token with a receipt opens the first-receive prompt.** `TokenService.restore` writes rows without the `onTokenAdded` emit that trusts an added token (`apps/extension/src/wallet/services/token/service.ts:853-896`), and no backup slice carries trust (`apps/extension/src/wallet/services/backup/backup-migration-registry.ts:195-216`), so each restored token with a receipt, a default seed included, asks again.
