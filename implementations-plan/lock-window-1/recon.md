## Claims checked

- **#1218 B1 holds.** `runWorker` (`transaction/service.ts:497-517`) gates a batch on `getActiveProfile()` once; `updateTx` (`:573-627`) and `checkFinality` (`:634-649`) then await the node and commit under the tx lock with only a watch-identity check. `applyReceipt` (`:745-751`), `clearInclusion` and `commit` (`:654-671`) mutate the watched object before the write, so a refusal after the mutation would leave memory ahead of storage. The poller also settles a switched-away profile's rows while another session is live; `sealed-transactions.composition.test.ts:270-293` pins that, and `updateTx`'s comment (`:575-582`) designs for it.
- **#1218 B2 holds, and refusing it is harmful.** `reconcileFromTx` (`auth-registry/service.ts:180-192`) has no session check. It is the only trigger for an authwit row's pending → mined change; a refused write leaves the row pending against a mined transaction, and the Finalized commit is its only second chance.
- **#1218 B3 holds, and the issue understates it.** `updateMarker` (`token/seeder.ts:376-391`) and `commitSeedResult` (`:610-637`) write the marker with only the purge epoch checked; a lock does not bump it. The token row is fenced only at `addSeededToken`'s entry (`token/service.ts:677-693`); `persistToken` / `advanceAdd` (`:425-527`) check the deletion epoch and the network, not the session.
- **#1218 B4.** The lock window holds for `updateFpcAddress`, `updateFpc` and `deleteFpc`. Separately, `updateFpcAddress` writes `{ ...existing, address }` (`fpc/service.ts:396-397`) from a row read before its PXE calls (`:351`), outside the lock, so a rename or a chain purge in that window is overwritten or written back. `EditFpcPopup.vue:138-143` shows a raw error message.
- **#1218 B5 holds, and refusing it is harmful.** `setRegistryEnabled` → `waitForTxProven` → `applyStatus` (`auth-registry/service.ts:419-461`, `:614-631`); `revokeAuthwits`' prune (`:403`) has the same shape. The comments at `:403` and `:450` keep both across a switch, and the popup reads only the stored status (`composables/useAuthRegistryStatus.ts`; `syncRegistry` has no popup caller). A refused write leaves the toggle showing the old state.
- **#1218 B6-B9 hold.** `addToken` / `addTokenAuthorized` (dApp `registerToken`) / the seeded add, `addNetwork` / `addEndpoint` / `updateEndpoint`, `createAccountInternal` / `importAccount` (a session check at entry only: `getProfileSecret` / `getProfileDek`), `addDappSession` (the MAC-key derivation refuses a locked session; the sign and seal after it do not), contacts without a run fence. The incoming-transfer `addAccount` cursor reset (`incoming-transfer/service.ts:488-532`) is what makes a new account's history findable; `createOperation` (`operation-journal/service.ts:259-345`) records work the person started.
- **What a person sees if a person-asked write were refused.** The row is missing after the next unlock, at every site. In addition: `addNetwork` shows a different error toast on the lock screen (`NewNetworkPopup.vue:88-134`); a refused token add leaves a failed import row for 30 s (`TokensView.vue:53-86`) and rejects the dApp's `registerToken`; a dApp's connect fails. The popups that disconnect on hide (`NewFpcPopup`, `NewTokenPopup`, `NewContactPopup`, `EditContactPopup`) already see a rejection at the lock.
- **#1138 holds; line numbers drifted.** `decideLockLanding` is `lock-landing.ts:55-59`; `settle` (`app.vue:438-440`) only marks the session checked; the landing's state carries no `isLogined`. `awaitProfileActivation` resolves at `composables/unlockWait.ts:70-72`. Option (b) alone fails: `route-guard.ts:39-40` bounces `/popup/auth` back to Home while `isLogined` holds. `profile/new-profile-helpers.ts:52` has the same blind spot over a shorter tail. The model already expects a lock for `restoreHeld` with a competing restart after finalize (`tests/e2e/helpers/profile-chaos/model.ts:1200-1210`).
- **#1183 holds.** The lock screen is `popup/pages/auth.vue` only. `password` `:53`, `isWrongPassword` `:54`, `isPasswordType` `:59`; the profile-id watcher (`:322-327`) resets only `isTornImport`. An in-flight unlock discards itself on `moved()` (`:121-129`, `auth.test.ts:839`).
- **#1225 holds for the lock.** `export/account.vue` `resetFlow` (`:99-110`) runs on an address, profile id, profile type or chain change, not on a lock. `export/seed.vue` has no watcher at all: the issue's "resets on a profile switch" does not hold for it. Both routes are auth-required, so the page unmounts on the ordinary lock; the gap is the window between `seal()` and the push, and a lock the next unlock supersedes before the landing (`unlock-method.test.ts` `lockThenUnlock`).
- **#1186 does not hold at this base.** `SECURITY.md:119-122` reads "A session opened from then on, under either unlock, also persists a silent-restore bearer", and `:182-188` says lenient mode keeps a passkey session's bearer. #1142 (518170a18) rewrote both sentences after the issue was filed. The behaviour is pinned by `profile/unlock-method.composition.test.ts:176-190` and `profile/service.passkey-unlock.test.ts:744-749`.
